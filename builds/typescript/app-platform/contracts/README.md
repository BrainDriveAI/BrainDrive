# First-party app contract foundation

Stable content-free Resume validator rule IDs are admitted only on deterministic-validation attempt diagnostics. Attempt diagnostics may add only a bounded duration class and, for structural failures, the coherent structural subtype (`empty_output`, `invalid_json`, `purpose_schema_mismatch`, or `host_normalization_mismatch`). Terminal General recovery diagnostics retain separate provider, targeted-repair, and applicable full-constructor rule-ID arrays alongside coherent safe-code and disposition fields; raw findings and owner content remain excluded.

This directory is the executable contract boundary shared by the BrainDrive app platform and reviewed installed apps. Resume Builder and Brief Builder are independently developed apps, not BrainDrive first-party product modules. These contracts provide generic authority and transport; app-specific workflow and inference policy stays in each signed app package. Importing these modules alone does not register a route, start a process, create storage, call a provider, or enable an app.

The generated model-compatibility entry schema reads legacy v1 records and strict v2 evidence. V2 retains every content-free run outcome and binds exact identity/configuration/policy/schema/corpus, three unique operations per fixture, decomposed success/recovery/failure counts, evidence class, validity, p95 latency, and an exact 90-day expiry. Legacy records remain readable but are classified by the runtime as provisional rather than release evidence.

## Generic first-party registration

`app-registry.ts` defines canonical lower-case app, publisher, route, capability, and inference-purpose identifiers; safe catalog presentation; manifest revision 2; verified package joins; independently reviewed capability/purpose/data-adapter registrations; and the immutable resolved descriptor. `../registry.ts` builds exact app-ID and route-key indexes without reading packages, owner data, or runtime state. Construction is deterministic and side-effect free. Duplicate or folded identities, unsafe metadata, package/registry identity disagreement, and missing reviewed bindings fail closed.

A manifest declares package files and requests authority. It cannot name a host handler, module/import, inference policy, or data adapter. The host registration uses bounded opaque binding IDs that identify reviewed compiled composition; it does not load a manifest-provided path. Generic capability and purpose identifiers are bounded syntax, not grants: the existing Resume capability and purpose enums remain closed product-specific policies, while a generic request becomes resolvable only when the host registration contains the exact app-scoped name and version.

Manifest revision 2 may now add an optional `presentations` declaration for generic app workspace contracts. The declaration is strict and non-executing: `AppPresentationProfileSchema` distinguishes existing `surface` profiles from future `chat_workspace` profiles, and `ChatWorkspaceDescriptorSchema` declares only bounded document ids, digest-bound app resources, purpose-limited context requests, and action descriptors. `primary_resource` remains required for the existing sandboxed surface path, and a surface presentation must bind that same `ui://` resource. App resources must bind declared read-only package files by path and digest. Context and action descriptors may reference only capabilities or inference purposes already requested by the manifest; they cannot name handlers, modules, provider credentials, host paths, filesystem destinations, or arbitrary owner-memory traversal. `ResolvedAppDescriptorSchema` projects the optional presentation set as metadata for later session/UI/action milestones, but these contracts alone do not create a workspace session, expose a model tool, or launch a view.

Revision-1 `PackageManifestSchema` is the installed Resume compatibility format. `LegacyResumePackageManifestSchema` and `parseLegacyResumePackageManifestForMigration` make that boundary explicit; the schema accepts only the canonical Resume identity, so another app cannot use it. New generic candidates must use `GenericPackageManifestSchema` revision 2. Milestone 1 does not switch the active package verifier or migrate stored state.

All authority-bearing envelopes are strict: unknown fields fail. Durable owner-data records use an explicit `extensions` object so a compatible reader can preserve unknown extension fields without granting them authority. The active data schema is version 4: current packages read versions 2–4 and write only version 4. Schemas 0 and 1 remain migration inputs through the staged 0→1→2→3→4 startup chain, not current package compatibility claims. Unknown newer versions and destructive downgrade attempts fail closed.

`InterviewTurnAuditSchema` is the one recognized content-bearing version-1 source extension for submitted Resume Builder interview provenance. It requires opaque turn/session identities, prompt version, topic, exact owner-visible question, submitted answer or skip, optional visible follow-up outcome, action, and occurrence time. Cross-field validation rejects answers on skipped turns, missing answers on answered turns, follow-ups on skips, and inconsistent follow-up outcomes. It excludes keystrokes, unsent input, hidden/system prompts, internal reasoning, provider payloads, and credentials. The extension is durable owner data; capability/lifecycle audit contracts remain content-free.

Schema-2-and-newer interview progress carries the exact acknowledged recovery slot/value/time/revision and last submitted turn identity. Schema 3 adds strict coverage, strategy, target-fit, historical craft-report, single-repair, and artifact-parity records. Schema 4 adds the corrected score-free craft-report v2 authority, the seven-value owner quality-state vocabulary, approval evidence v2, Career return metadata v2, and the synthetic frozen-regression manifest. Historical craft/approval and repair-operation v1 records remain readable; historical review derives only `pre_correction_review` and is insufficient for a corrected new approval. New repair-operation v2 records bind one `repair_statement` action, one correction class, exact statement scope, same provider/model, input/output and source/report digests, terminal transition, safe recovery reason, and optional successor identities. An artifact-parity report requires all five unique representations, a disposition consistent with its mismatch categories, and a digest over its complete non-envelope body. Coverage keeps non-fact dispositions separate from career facts; only answered job evidence is writable as a schema-3-or-newer career fact. The bridge `capability.call` may carry a separate `request_operation_id` for semantic retry while `message_id` remains transport replay/correlation identity. The strict recovery lifecycle projection distinguishes unresolved current-process absence from settled restart absence after verified store transaction recovery. Inference terminal diagnostics can distinguish provider validation from ordered targeted/full local recovery using only an all-or-none coherent set of allowlisted failure codes, candidate classes, validator-code arrays, and dispositions. Recovery and persuasive-quality diagnostics otherwise use the same strict content-free event body: only allowlisted IDs, enums, counts, timings, and digests are admitted; owner text, resume/job content, prompts, provider bodies, reviewer transcripts, credentials, and paths remain prohibited.

Package verification authority is split deliberately: `PackageManifestSchema` describes archive identity and contents, `PackageDescriptorSchema` binds canonical manifest and exact archive digests to an Ed25519 signature, `PackageSourceIndexSchema` resolves immutable descriptors, `TrustRootSchema` defines the pinned-root/release-key hierarchy, and `RevocationListSchema` supplies monotonic explicit denials. Current first-party fixtures retain the required Docker Linux x64 and desktop Windows x64 artifacts and may add exactly one `desktop_macos_universal`/`macos`/`universal` packaged-Node artifact with a matching signed `desktop_macos` source. Existing two-target signed packages remain valid; a macOS host fails closed unless the selected package and source index both authorize the macOS target. `supervisor.ts` freezes the runtime-neutral control protocol; it does not implement or start a supervisor.

`lifecycle-foundation.ts` freezes seven separated storage classes, mixed-version fail-closed behavior, and the opaque Spec 02 lifecycle-data adapter. `audit.ts` defines the strict lifecycle diagnostic allowlist. These contract modules expose no downloader, store, process launch, registration, persistence, API, or UI entrypoint.

`audit.ts` also defines the strict content-minimized Spec 10 Resume recovery reconciliation detail contract used by the ordinary JSONL sink and support-bundle projection. Its additive fields are opaque IDs/digests, revision/count/timing classes, idempotency/final/conflict dispositions, and a safe error code; it has no owner value, prompt, endpoint, credential, or path surface.

Spec 10 Milestone 5 adds a separate strict ordinary-audit contract for explicit General Resume retries. Uniquely named fields retain only the `owner_initiated_retry` class, prior/new operation IDs, semantic-input digest, frozen strategy/provider/model identities, and authoritative equivalence result. The support-bundle sanitizer preserves that bounded relation while dropping generic reason fields and all owner content, prompts, provider bodies, endpoints, credentials, and paths.

The generated Spec 10 authorities also include the strict recovery reconciliation query and operation-lifecycle projection. The latter is a content-free host/package read contract and converts directly into the shared reconciliation decision's host-settlement and operation-readback inputs.

The valid trust/source/revocation/package-signature fixtures contain mutually verified public keys and signatures. Their one-time private keys were discarded and are not present in the repository, so later runtime fixture generation must use an ephemeral test trust root or release-authority-provided signing material rather than treating conformance vectors as signing credentials.

JSON Schema artifacts are generated from the Zod authorities with `npm run contracts:schemas` from `builds/typescript`. Generic artifacts use the `app-platform/v1` schema namespace; retained Resume-specific artifacts keep the `resume-builder/v1` namespace. Generated artifacts are checked for drift by the contract tests.

Spec 09 adds an additive, content-free terminal inference vocabulary in `inference.ts`. New results and app inference events may carry strict outcome metadata for the normalized stage, finish category, bounded attempt count, retryability, recovery class, completion mode, and final disposition. Previously persisted version-1 results and events without that optional metadata remain readable. Legacy error codes remain parseable, while new outcomes can preserve malformed structure, incomplete output, evidence rejection, provider schema/authentication/authorization failures, filtering/refusal, unexpected tools, cancellation, and internal failure without carrying provider payloads or owner content.

The accepted physical namespace is the existing repository-consistent `apps/resume-builder` mapping below the configured memory root. These contracts do not initialize or write that namespace. Data operations use exactly `career.context.read`, `career.facts.read`, `career.facts.propose`, `career.facts.confirm`, `resume.definitions.read`, `resume.definitions.write`, `resume.jobs.read`, `resume.jobs.write`, `resume.artifacts.register`, `resume.export.request`, and `resume.operations.read`; inference remains a separate host capability. The inference allowlist now includes `resume_strategy`, version-2 `tailoring_plan`, `resume_craft_evaluate`, and `resume_craft_repair`. Every purpose remains fixed-policy, bounded to two attempts and one concurrent call, provider-brokered, and no-tools.
