# Modern MCP Apps host

For the reusable whole-system ownership, lifecycle, scaling, and app-development model, start with the [installed app architecture guide](../../../../docs/developers/integrations/installed-apps.md). This page remains the source-adjacent authority for MCP negotiation, sandbox, bridge, token, capability, and session behavior.

This directory began as the Spec 05 host boundary. Its facade, routes, resource selection, and session/view authority are app-neutral. Installed apps own their workflows, document meanings, action semantics, artifacts, and app-specific inference programs; the host supplies generic authenticated transport, provider mediation, document storage authority, capability dispatch, artifact/export mediation, cancellation, and policy enforcement. Reviewed app adapters bind app-owned requests to those host services or to explicit compatibility domains without adding action-id branches to the generic host. It does not implement marketplace discovery, general MCP prompts/completions, or remote OAuth.

## Host flow

1. `AppMcpHost` delegates to the reviewed adapter for the route-selected app; that adapter resolves the active installation and its private loopback runtime connection from the lifecycle supervisor.
2. `ModernMcpAppsClient` negotiates exactly MCP `2026-07-28` plus `io.modelcontextprotocol/ui` `2026-01-26`, requiring both tools and resources before any resource read.
3. The client lists tools/resources and reads only the exact verified manifest `primary_resource.uri`. It retains complete list/read metadata internally, validates media type, size, digest, cache, and same-server identity, and rejects HTML that violates the fail-closed content policy.
4. The host creates an installation/view/operation/session-bound bridge, consumes the raw one-use bootstrap token, and returns only opaque IDs plus the validated UI projection to the authenticated owner client.
5. The trusted web component loads a fixed `data:` sandbox proxy with `sandbox="allow-scripts allow-same-origin"`; the proxy and host therefore remain different origins. Only after the proxy-ready message does the host send the validated resource through `ui/notifications/sandbox-resource-ready`. The proxy creates the inner opaque-origin view with `sandbox="allow-scripts"`, injects the restrictive resource CSP, and mediates every message.
6. The component implements Apps `2026-01-26` initialization (`ui/initialize`, host response, then `ui/notifications/initialized`) and emits only safe host context. The view never receives the launch/session record, bridge token, server identity, owner permissions, raw paths, or Tauri globals.
7. The gateway accepts only the typed, host-constructed Apps bridge envelope for that owner session. Same-server app-visible tools and the validated launch resource are allowed. A consumed capability token is reduced to its exact authority and the current lifecycle grant is rechecked before work. Installed-app inference uses a one-use `app_inference` token: BrainDrive may call private model-visible prepare/adjudicate tools on the same verified app connection, but the sandbox cannot. Provider execution remains credential-isolated, structured, no-tools, and limited to two calls. Export uses a one-use `app_export` token and the host-owned browser-save boundary. Cross-server/private-tool iframe calls, undeclared host actions, stale, replayed, revoked, malformed, oversized, or wrongly bound messages fail closed.

Disable, update, uninstall, lifecycle generation change, expiry, explicit session close, iframe/page teardown, and gateway shutdown remove bridge-session authority. Temporarily hiding the BrainDrive document or navigating to another BrainDrive surface does not itself close the live view. The sandbox receives no bearer credential, owner permission object, host path, filesystem/Tauri API, arbitrary network permission, download authority, or unrestricted MCP endpoint.

## App-chat session authority

The app-chat workspace path is additive to the sandbox bridge. A manifest revision-2 package must declare a `chat_workspace` presentation and matching workspace descriptor before the host can open an app-chat session. The host does not fall back to an app-specific workspace when descriptors are absent, malformed, or a surface presentation is requested.

Catalog routes may expose owner-safe presentation summaries so the web client can route a visible primary chat presentation to this path. Those summaries are not authority: the launch call still reselects the presentation from the verified manifest and rejects surface, hidden, stale, malformed, or cross-workspace requests.

`AppChatSessionRegistry` allocates opaque session, view, and operation identities and binds them to owner, account, actor, app, publisher, installation, package digest, lifecycle generation, grant id, grant revision, revocation generation, presentation id, workspace id, and a digest of the granted context set. Exact reconnect rotates the session identity and session generation while preserving the view and operation identity; stale, cross-presentation, cross-workspace, cross-package, grant-revoked, grant-revised, lifecycle-stale, disabled, or digest-mismatched sessions fail closed.

App-chat context projection is limited to the selected workspace descriptor. The first implemented projection source is Career context through the existing host-mediated `career.context.read` app-data capability. Unsupported optional context requests are projected as unavailable metadata; required unavailable context rejects launch. The projection contains bounded content plus opaque digests and does not include app-held bearer credentials, host paths, owner permission objects, provider endpoints, or arbitrary memory traversal.

## Native model-session actions

When a native chat turn carries a valid `app_chat` metadata envelope, the gateway asks the route-selected `AppMcpHost` for a one-turn app-chat model context. The host rechecks the opaque session against current lifecycle, package digest, grant revision, revocation generation, presentation id, workspace id, view id, operation id, session generation, and context grant-set digest before any provider call.

The model context is assembled from app-owned descriptors only. Text resources are read from immutable package files, verified against their declared content digest, bounded for prompt size, and included only when their prompt-inclusion policy allows model-session use. App-chat empty-state copy, CTA labels, CTA chat prompts, workspace documents, document renderers, and document header actions come from the verified workspace descriptor; the web client only renders the reusable BrainDrive chrome. The prompt names package-internal paths and digests, not host filesystem paths, bearer tokens, provider credentials, owner permission objects, or bridge authority.

Model-visible app actions are created as per-message dynamic tools named from the descriptor action id. Hidden actions are not exposed. Each tool embeds the app-declared concrete input JSON Schema under `action_input` and adds the host operation/idempotency fields required for the session boundary; schema-ID-only actions fail closed before exposure. Each tool remains bound to the active session metadata captured for that turn and rechecks current authority again at execution time. The host treats the action id as opaque. When the active runtime exposes the private model-visible `app.actions.plan` tool, the action may declare zero or more required host capabilities, and BrainDrive asks the app to translate the opaque action into a strict ordered plan of generic `capability.call`, `document.read`, `document.write`, and `export.prepare` steps. Without a runtime planner, V1 model-session actions must declare exactly one host capability, and BrainDrive dispatches the app-provided input directly through the generic app capability dispatcher keyed by app id, capability name, and version. The dispatcher validates both input and result against reviewed host registrations, not against app-name branches in this host. Required idempotency keys are enforced at the model-tool and dispatcher boundary; equivalent retries reuse the existing dispatcher result and mismatched retries fail closed.

## Reconnect and concurrent views

`AppViewRegistry` is the host authority for live app view state. Composite indexes bind app plus session/view identity, so identical opaque IDs in different apps cannot collide or close one another. A first launch allocates random session, view, and operation identities at bridge generation 1 only after lifecycle activation, authenticated supervisor readiness, MCP negotiation/discovery, resource verification, and sandbox eligibility all succeed. A reload may present only the previous session, view, operation, and bridge generation. An exact current match keeps the view and durable operation identities, rotates the session, increments the bridge generation, and invalidates the old session before it can commit or render another result. A missing, stale, expired, cross-app, cross-installation, cross-package, cross-lifecycle, or racing resume request fails closed.

The registry permits at most 16 live views per installation and expires inactive records after five minutes. Each view has independent session, token, progress/result, cancellation, focus, and close authority. Cancellation and close resolve the exact current session and operation; they never search other views for a matching operation. The existing capability and inference coordinators remain the durable idempotency authorities, so reconnect changes transport identity without creating a second write, export, or provider call.

`parity-normalizer.ts` compares Docker and selected packaged-desktop observations after separating only the five M1-contract runtime fields: transport, process isolation, package-root reference, cache-root reference, and diagnostic platform. Protocol, extension, lifecycle, policy, state, error, and outcome differences remain failures. A missing selected target produces blocked evidence rather than an inferred parity result. The revision-bound M7 result and operator checks are recorded in [`SPEC-05-M7-ACCEPTANCE.md`](SPEC-05-M7-ACCEPTANCE.md).

## Compatibility boundary

The modern installed-app path is independent from fixed tool discovery. Existing `mcp/config.ts`, `mcp/registry.ts`, and `tools.ts` still discover the three fixed services, and `mcp/client.ts` applies the explicit legacy compatibility projection only at the ordinary agent-tool boundary. Internally, modern app results retain every accepted content block, annotation, resource link/embedded resource, `structuredContent`, `_meta`, error state, progress identity, and cancellation identity. Milestone 4 additionally routes declared `capability.call` messages through reviewed app adapters, including the Resume compatibility adapter documented in [Resume Builder data domain](../../resume-domain/README.md). Installed-app inference routes only through the generic no-tools executor and the active app's private program tools; Resume contract version 1 is rejected. Owner confirmations are authenticated host actions, but app-specific transition meaning remains in the app package and reviewed adapter.

Spec 05 M2 replaces the former initialization-shaped exchange with the official v2 client pinned to MCP `2026-07-28`. `AppMcpHost` shares one connection manager across launches; connection authority is keyed by installation/server and bound to app, publisher, package digest, runtime identity, and generation. Discovery is atomic across tools, resources, and resource templates. Matching authority reuses the connection, changed/stale authority closes it, read-only negotiation/discovery may reconnect once, and ambiguous tool calls are never replayed. The manager preserves complete results and derives separate model/app projections, validates exact Apps visibility and same-server identity, and verifies `ui://` resource MIME, size, digest, cache identity, and redirect policy before the existing host consumes the resource.

Fixed tools remain deliberately separate: `mcp/host/legacy-adapter.ts` wraps the existing SDK-v1 `2025-11-25` list/call behavior, naming, approval classification, context headers, typed failures, and lossy chat projection. `builds/mcp_release` receives no installed-app authority. The M2 protocol core is documented in [`mcp/host/README.md`](../../mcp/host/README.md); it does not add renderer messages, named capabilities, inference, dynamic server launch, subscriptions, or supervisor lifecycle behavior.

## Sandbox renderer and policy bridge

Spec 05 M3 keeps the trusted React component, intermediate proxy, and app view as three authority layers. The outer proxy contains only fixed code plus a random binding nonce; neither the resource HTML nor any launch identity appears in its URL. It accepts host traffic only from its exact parent with the channel/direction/nonce wrapper, accepts view traffic only from the exact inner window at origin `null`, and forwards no other source. The inner view has no same-origin, forms, object, worker, popup, navigation, download, device, clipboard, storage, cookie, parent-DOM, direct gateway, or Tauri authority. Its packaged SHA-256 and UUID helpers use only `TextEncoder`, arithmetic, and `crypto.getRandomValues`, which remain available under the opaque origin. Trusted host-side app identities use the same `crypto.getRandomValues` primitive through the shared browser crypto helper, so LAN HTTP does not depend on the secure-context-only `crypto.randomUUID` API.

`McpAppBridgeController` enforces proxy-ready/initialize/initialized ordering, exact JSON-RPC and compatibility-message schemas, unique IDs, 64 KiB payloads, depth 32, 100 messages per 10 seconds, 16 outstanding requests, cancellation, late-result discard, resize bounds, generation teardown, and default-deny methods. `ui/message` and `ui/update-model-context` are explicitly rejected so app content cannot enter model context. The trusted gateway adapter constructs the installation/view/operation/generation/provenance envelope; the app does not construct authority claims or hold a runtime credential.

`BrowserActionBroker` permits only configured HTTPS origins, host gesture plus confirmation, bounded clipboard writes, and allowlisted export MIME/size/name. The current Resume Builder policy allows `https://docs.braindrive.ai`, clipboard write up to 16 KiB, PDF export up to 2 MiB, and strict UTF-8 `text/plain` export with a `.txt` filename. The host performs Copy and save actions and returns only a safe outcome or destination label. All other schemes, origins, clipboard reads, direct downloads, raw paths, mismatched extensions/MIME, and unconfirmed actions fail closed.

## Capability boundary

The [capability registry](../../app-capabilities/README.md) contains eleven version-1 data/export actions plus the M5 `app.inference.request` action. For every action the host derives the owner, actor, app, publisher, package digest, grant/revision, revocation generation, installation, connection, view, operation, idempotency, audience, capability, and record scopes. The token broker verifies those claims against the current lifecycle grant, permits one exact use, and revokes at installation, connection, or view closure. Equivalent concurrent and completed retries coalesce through the operation coordinator; canonical input mismatch conflicts before the selected adapter.

For data capability calls, `message_id` remains a unique per-session transport replay identity. The optional `request_operation_id` is a separate semantic identity for durable retries such as recovery saves. The host derives one-use authority and idempotency from that semantic identity while retaining the unique message ID as correlation. This permits response-loss reconciliation without permitting a bridge message replay; different canonical input under one semantic identity fails closed.

Recovery-save host diagnostics use the strict `app.resume_recovery.reconciliation` detail contract. They retain only the operation/semantic digest, expected revision, timing and reconciliation classes/count, idempotency disposition, final disposition, conflict class, and safe error code. Values, questions, record paths, endpoints, prompts, candidates, tokens, secrets, and credentials are not fields. A pre-commit `resume.operations.read` 404 remains `not_found_within_scope` for compatibility and is pending under the shared Spec 10 cadence; committed reads retain their existing result shape.

Recovery reconciliation is an additive mode on that same authorized reader: `{ queried_operation_id, reconciliation: "resume_recovery_v1" }`. It returns a strict `recovery_reconciliation` object distinguishing `pending`, `completed_without_operation`, `committed`, `cancelled`, `failed`, `conflict`, `current_process_lifecycle_unknown`, and `quiesced_restart_no_operation`. Committed results retain the legacy `record` and `results` fields. Current-process unknown lifecycle has null binding fields and is never terminal. The production gateway initializes and transaction-recovers the owner-data store before constructing one Resume host adapter for that process. A process-instance-scoped registry prevents another adapter in the same process from treating a live operation as absent; pending evidence is never evicted, while settled cross-adapter evidence has a fixed retention bound. Only a subsequently initialized process generation with no durable operation or current-generation binding emits the settled restart/no-operation variant. In-memory lookup additionally requires the original app, installation, owner, actor, grant revision/generation, and exact record-scope set; durable committed lookup continues through the scoped owner-data operation record.

Sandbox actions keep bearer authority entirely in the host session. App-server actions use `POST /internal/apps/:appKey/capabilities` with a short-lived one-use bearer and the configured gateway internal transport credential. The route resolves the registered app key before reading its request body or app state and does not accept owner authentication as app-server authority. The selected adapter receives only the verified authority projection and rechecks connection/view/current-grant identity. Export destination selection and bytes remain top-level host actions; only safe status, label, and opaque artifact identity cross the app boundary.

Generic artifact/export routes expose that same boundary without Resume-specific request shapes. `POST /apps/:appKey/artifacts/register` records host-authorized artifact metadata only. `POST /apps/:appKey/exports/request` prepares host-confirmed bytes under a safe label and destination intent. `POST /apps/:appKey/exports/finalize` records only the generic safe receipt projection for current app/export flows; any legacy adapter compatibility is isolated outside the generic route contract. Unsafe labels, raw destination paths, unconfirmed exports, unconfirmed overwrite intent, stale authority, and app-route mismatches fail before an app can write to an owner destination.

Inference tokens use only the `app_inference` audience and exact inference capability. The [installed-program executor](../../app-inference/README.md) validates the versioned generic invocation, invokes private prepare/adjudicate tools on the same verified app connection, resolves the owner-active provider, and permits at most two sequential structured no-tools calls. The terminal result may return opaque provider/model identities because an app can bind persistence to the exact selected configuration; it never returns credentials, secret references, authorization headers, endpoints, policy messages, raw provider bodies, or filesystem authority. Prompts, output schemas, semantic validation, content-free issue IDs, the one correction instruction, and eligible deterministic fallback remain app-owned. Configuration recovery opens the existing BrainDrive Settings modal and adds no app-owned selector. When an action needs independent owner confirmation, the trusted host issues the reviewed confirmation projection and records the decision; the app owns the action meaning and the later state transition.

## Owner routes and web surface

When `BRAINDRIVE_APP_PLATFORM_ENABLED=true`, the existing owner-administration lifecycle routes are joined by one app-parameterized family used by the reviewed Resume Builder and Brief Builder registrations:

- `POST /apps/:appKey/launch`
- `POST /apps/:appKey/bridge`
- `POST /apps/:appKey/apps-bridge` for host-constructed, session-bound Apps JSON-RPC requests
- `DELETE /apps/:appKey/sessions/:sessionId/requests/:operationId` for one request cancellation
- `DELETE /apps/:appKey/sessions/:sessionId`
- `POST /apps/:appKey/chat-workspaces/launch` for a descriptor-backed native app-chat workspace session. The route reselects the verified manifest presentation/workspace, binds context grants, and returns only owner-safe session, presentation, workspace, and context projections.
- `GET /apps/:appKey/chat-workspaces/sessions/:sessionId` for current app-chat session inspection after authority revalidation.
- `GET /apps/:appKey/chat-workspaces/sessions/:sessionId/documents` for the selected workspace's current app-owned document list.
- `GET`, `PUT`, and `DELETE /apps/:appKey/chat-workspaces/sessions/:sessionId/documents/:documentId` for app-owned document read, revision-CAS write, and retention-bound deletion through the generic document store.
- `POST /apps/:appKey/data/call` for host-owned owner actions; failures use the content-free `{ error, owner_state }` contract. When independent host policy requires confirmation, `error.confirmation` adds only the exact capability identity and the reviewed title/action label; app input cannot supply or override that projection.
- `POST /apps/:appKey/artifacts/register` for host-authorized artifact metadata registration. The route injects authority from the selected app installation and never accepts raw destination paths.
- `POST /apps/:appKey/exports/request` for host-confirmed export preparation. The route accepts safe filename labels, bounded PDF or text bytes, destination intent, and overwrite confirmation state, then delegates destination handling to the trusted host.
- `POST /apps/:appKey/exports/finalize` for safe receipt recording after the trusted browser or native save boundary reports a terminal outcome. Generic receipts expose only opaque identities, digest, media type, outcome, and safe destination label; compatibility finalization stays isolated behind reviewed app adapters.
- `POST /internal/apps/:appKey/capabilities` for authenticated app-server capability calls; this is not an owner route and requires an exact one-use capability bearer

The web client exposes one top-level `Apps` sidebar entry. It renders the deterministic `/apps` catalog through one reusable card pattern showing exact app/publisher identity, lifecycle and operation state, installed/available version, precise first-party trust and revocation status, source, host/protocol/data compatibility, requested/granted capabilities, primary resource, and selective-retention disclosures. After first use, the Apps workspace remains mounted while the owner navigates to another BrainDrive surface, so returning to Apps reveals the same selected iframe and in-memory workflow state. Browser-tab visibility changes are also non-terminal; explicit Close, page teardown, lifecycle invalidation, or host expiry still ends the session. Privileged controls come only from the host's `available_actions`; busy, error, ambiguity, confirmation, launch, reload, cancel, close, and focus state are scoped to the selected app/session. Uninstall uses a focus-managed confirmation generated from host retention policy. Ambiguous transport completion refreshes only the selected app before the UI claims an outcome. States use readable text in addition to color, the catalog starts as a responsive single column, and closing the generic iframe returns focus to the selected card's Launch control. App-specific compatibility actions, including Resume/Career integrations, remain in reviewed app adapters rather than the generic host.

It denies Career return, export, server-origin authority, and non-direct entry rather than delegating to the Resume adapter.
