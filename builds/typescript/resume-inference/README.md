# Retired Resume inference broker and offline conformance evidence

This directory contains the retired pre-installed-program inference implementation and its offline conformance, quality, and historical acceptance harnesses. It has no production caller. All twelve active Resume purposes are owned by the Resume Builder package at `builds/resume_builder/resources/inference-program.js`; BrainDrive's generic executor is in `app-inference/installed-program.ts`, and contract version 1 is rejected.

The material below documents historical version-1 behavior and the validators still reused by host-side Resume data-safety checks and offline tests. It is not the authority for any installed app prompt, schema, semantic issue ID, retry instruction, adjudication, or fallback.

For the v3 General envelope, semantic binding failures use content-free missing, duplicate, foreign, heading-shape, heading-support, bullet-shape, bullet-support, and top-level-leakage IDs. The single structural retry receives only the precise failed relation and unchanged immutable snapshot; it receives no owner value or malformed provider output.

Evidence-validation retries group duplicate findings by their safe code, content-free validator rule ID, safe message, and scope, with a bounded set of affected statement IDs. Statement-scoped findings may change only those statements. Global findings receive only their named rule's narrow correction permission: reduce a job to six experience bullets, insert an already-existing section into strategy order, or remove unsupported wording from named statements. Attempt audit, terminal recovery, and the live dense/holdout diagnostic retain only allowlisted rule IDs, bounded timing classes, structural failure subtypes, and content-free schema issue IDs, making attempt-1/attempt-2 comparisons possible without retaining candidate text or malformed values.

This directory is the accepted Spec 03 broker plus the Spec 06 implementation and the accepted Spec 07 quality-gate-correction work through Milestone 6. `resume_strategy`, score-free `tailoring_plan`, independent `resume_craft_evaluate`, typed correction routing, bounded `resume_craft_repair`, and the controlled-quality evidence contracts are operational. Spec 05 M5 exposes the broker through the thin [protected app capability adapter](../app-inference/README.md). Both remain deliberately separate from `engine/loop.ts`: requests cannot discover or call tools, cannot enter the chat retry loop, and cannot select a provider, model, credential, or capability.

Current repair consumes report v2 evidence only. Every blocking finding must resolve to negative statement evidence under one correction class before the host exposes a repair scope. The validator rejects title, order, statement-set/shape/support, unflagged-statement, and no-op drift. A syntactically valid result is still only a candidate: the domain reruns all deterministic, mechanical, anchor, and craft checks, and a regression produces no successor. Explicit absence selects at most one existing qualitative-first deterministic coverage opportunity; inference cannot create or confirm a fact.

`ImmutableInferenceSnapshotBuilder` resolves only exact, scoped revision IDs and admits only confirmed factual evidence. Historical schema-2 job-evidence dispositions other than `answered` remain readable but are filtered out of the fact snapshot and its revision manifest. Strategy receives confirmed facts, exact coverage heads, deterministic evidence annotations, presentation preferences, and accepted `resume-quality.md` revision-3 identity. General generation receives those exact facts and coverage heads plus one persisted strategy and the same quality identity; zero, contact-only, and role-heading-only inputs fail before provider resolution because they contain no substantive draft evidence. Craft evaluation receives one current proposal, strategy, optional target analysis, host-derived truth/structure/mechanical gate evidence, independently extracted content-minimized C1–C3 anchors, and the accepted RB7-OQ-1 implementation-blocker identity. The app cannot supply or override deterministic gate or anchor blocks. Interview assistance uses `resume.interview-assist.v2`: the host supplies the exact ranked opportunity, and prompt policy 12 permits the model to phrase it only. `ResumeInferenceBroker` validates the request and every data-block digest before resolving the owner's live provider, then uses `completeStructuredNoTools` with `tools: []`, fixed prompt policy 12, strict purpose schemas, bounded token/time/attempt limits, and the caller's abort signal.

Strategy inputs use one shared canonical form before snapshot digesting, broker submission, persistence validation, and synthetic synthesis. Facts are grouped by semantic class and job association, jobs use parsed end/start chronology with immutable revision identity only as the final tie-breaker, coverage uses job then coverage-revision identity, and evidence annotations use association, class, priority, then fact identity. Equivalent duplicate identities deduplicate; conflicting duplicates fail. Strategy arrays deduplicate and sort, and the supported non-omitted sections are restored from the confirmed snapshot in the fixed order `contact`, optional `summary`, `experience`, `education`, `certifications`, `skills`, `projects`, `leadership`, `volunteer`, `links`; a model cannot mark evidence must-use while silently dropping its section. Presentation or target direction remains context only and cannot create work, title, leadership, or proficiency evidence.

The broker never exceeds the accepted two-provider-call ceiling. `failure-policy.ts` normalizes the finish reason before parsing and gives each bounded structural, incomplete, deterministic-validation, operational, filtered/refused, tool-call, cancellation, and compatibility outcome one explicit decision. Empty, schema-invalid, oversized, or first-call length-exhausted output can use the second call for structural repair. That structural retry resends the unchanged immutable snapshot and adds a bounded instruction containing only allowlisted schema issue IDs; it does not echo malformed raw output or values. A schema-valid result that fails deterministic validation can instead use that call for an evidence-validation repair containing the prior structured result plus only compact grouped safe findings and rule-scoped correction permissions; the model must preserve every unflagged statement exactly. General provider responses use `resume.general-draft.v3`: every structured job owns one nested `heading_statement` and at most six nested `bullet_statements`, while the top-level statement array contains only non-experience sections. The host verifies each nested statement against immutable job evidence, rejects cross-role or top-level experience leakage, orders roles from the persisted strategy, then flattens and removes the provider-only envelope before validating or persisting the unchanged flat draft contract. General generation also states its deterministic host invariants directly: no more than six experience bullets per job, every statement section must occur in section order, and unsupported wording must be removed. A final incomplete General Resume response reaches its fact-backed fallback; an ineligible purpose returns `incomplete_output`. If both structured strategy responses are malformed or still violate deterministic lineage, the host reconstructs the canonical evidence-shaped strategy from the same confirmed snapshot and annotations. General drafts inherit the persisted strategy's exact section order. A redundant or bounded high-confidence ungrammatical summary is replaced with positioning assembled only from confirmed role, direction, skill, or prior-role evidence. After final eligible General evidence failure, local recovery is ordered: statement-scoped fact repair first, then complete deterministic General construction if the targeted candidate remains invalid. Multi-unit non-omitted evidence for one job dimension is combined into one supported bullet, section aliases follow the persisted strategy, and locally inserted identities are deterministic. Both candidates make zero provider calls and cross the exact parser, purpose schema, host normalization, and unchanged deterministic validator. A foreign-support targeted candidate therefore cannot persist, while a separately constructed valid fact-backed draft may complete as `deterministic_fallback`. If either local candidate remains schema- or evidence-invalid, no result completes. Authentication, authorization, compatibility, cancellation, content-filter/refusal, and unexpected tool-call outcomes never fall back or retry. Existing deterministic guidance preserves its approved local recovery for provider unavailability, quota, rate-limit, deadline, and internal operational failures; it makes no additional provider call and does not change resume content or provider authority.

`purpose-recovery.ts` classifies all twelve inference purposes and fails closed when a purpose is absent from the table. Deterministic recovery is limited to presentation of the exact host-ranked interview opportunity, canonical strategy, the fact-backed General Resume, bounded guidance projection, and host-owned craft evaluation. Interview presentation copies the selected job, opportunity, dimension, kind, and value category, derives a stable question identity, and cannot choose or broaden the topic. Craft evaluation remains a zero-provider-call host operation. Job analysis, evidence matching, tailoring, targeted drafting, revision classification/drafting, and craft repair have no semantic fallback; tailoring, targeted, and revision normalization after a valid provider result remains separate from fallback evidence. Every constructed result still passes its exact schema and the normal deterministic validator before completion.

Raw failed provider output is not retained or audited. Every new terminal broker result carries the additive content-free outcome vocabulary: exact stage, normalized finish category, attempt count, retryability, recovery class, completion mode, and final disposition. Each provider-attempt decision and terminal callback is parsed through its strict content-free schema. Attempt records contain correlation IDs plus bounded purpose, attempt, stage, finish, and decision enums; terminal records add policy/schema identity, safe model class, recovery/disposition, usage availability, duration class, and allowlisted validator codes. General evidence recovery additionally records the original safe failure code, provider-stage validator codes, the ordered local candidate classes, separate safe code/disposition fields for targeted repair and full construction, and the final recovery disposition. The protected app projection and support-bundle allowlist preserve these enums and arrays without validator messages, statement identities, prompts, immutable input blocks, owner resume/job text, raw provider output, credentials, endpoints, secret references, or private paths. Existing 14-day JSONL retention and 5 MiB rotation remain unchanged.

The host craft evaluator now binds C4 evidence to the actual summary and C3/C6/C7 evidence to the full bounded experience set instead of reusing one convenient statement. It blocks summaries that substantially repeat experience, near-duplicate experience statements, known mechanical phrasing, repeated openings, and bounded high-confidence grammar/fluency defects. Targeted drafting likewise requires each planned change to produce an observable word-level rewrite or an actual supported ordering improvement; punctuation, case, and whitespace alone produce the typed no-material-change result.

Cancellation is checked before and after provider resolution, before each bounded attempt, immediately after every provider response, and before validation/commit. A provider response that arrives after abort is projected as cancelled and cannot become a completed result. Broker idempotency hashes the immutable semantic request rather than host-generated request/timestamp fields, so a reconnect rebuild reuses the same completed operation while any snapshot, policy, schema, identity, or budget change conflicts.

The deterministic gate resolves every cited fact identity to the immutable confirmed snapshot, requires exact job source spans, validates targeted lineage, and conservatively rejects lexical/protected numeric, date, title, and URL drift. It treats bounded career-direction connectors such as “targeting” and “seeking” as presentation grammar, while the named role and every protected value must still resolve to confirmed support. Product craft report v2 adjudicates C1–C7 and T1–T3 without a score. Every verdict carries exact positive, negative, or explicit-absence evidence; missing, duplicate, foreign, stale, context-changing, or applicability-invalid references fail closed. Local C1–C3 anchors are implementation-independent necessary evidence and mandatory local failures remain authoritative over model output. Provider unavailability, malformed/incompatible output, disagreement, and stale bindings cannot create a passing report and project to `review_incomplete`. Under the accepted RB7-OQ-1 disposition, `evidence_limited` is durable and visible but is not ordinary product passage, owner-approvable, or release-ready. Historical v1 reports remain readable only as pre-correction evidence.

Target-fit analysis requires exactly one approved general resume, its persisted strategy, one immutable job snapshot, and one evidence matrix. The host adds the fixed `resume.target-fit-policy.v1` block and independently recomputes the provider plan. The current policy identity is `braindrive.resume-builder.target-fit.provisional-rb7-oq3` version 1: it is the draft plan's suggested default, not an accepted answer to open question RB7-OQ-3. It permits a child only for at least one supported core requirement, or at least two supported transferable requirements, plus a supported selection/order/emphasis change. Ambiguous evidence fails closed; shortening or wording-only changes cannot satisfy the material-change gate. Targeted drafting then receives the persisted passing analysis and may change only its named parent statements. Unsupported and partial rows never become claims, and target text cannot become a resume title or unplanned keyword change.

Guidance receives exactly one immutable resume definition and one deterministic quality-finding block. Results are bounded to strengths, gaps, ATS/structure observations, interview preparation, and at most three optional follow-up questions. Every item carries one of the supplied evidence labels; score, ranking, prediction, guarantee, and unsupported competence language are rejected. Malformed or unavailable provider output uses a deterministic local projection from the same finding block. It never becomes resume content and never changes approval state.

Resume-generation policy asks compatible models to follow the exact strategy's history shape, evidence priorities, role-density classes, section order, contextual skill placement, and optional summary decision. Density classes guide evidence selection and are not bullet quotas. Every must-use identity must appear with claim lineage or one visible bounded omission reason. Structured interview values keep a job and its accomplishments associated by an immutable fact revision, but their JSON markers and internal identities are forbidden from visible resume text. Coaching preferences can guide the draft but cannot be copied into experience. A summary is omitted when the snapshot cannot support distinct positioning.

## Compatibility gate

`ModelCompatibilityRegistry` reads both registry formats. Existing version-1 entries can provide only explicit `legacy_provisional` development continuity when their prompt policy is current, and never satisfy Spec 09 release evidence. The checked-in version-1 records bind prompt policy 8, so policy 12 intentionally makes them stale and the production compatibility gate fails closed until fresh conformance evidence is accepted. A current version-2 entry binds the exact provider profile and configured model, optional provider-returned model identity, a secret-free effective structured-inference configuration fingerprint, purpose, prompt policy, output schema, versioned fixture-corpus digest, every retained run, evidence class, and tested/expiry timestamps. It expires exactly 90 days after testing. Configuration/corpus/observed-identity drift, expiry, malformed or partial evidence, fewer than three unique operations per applicable fixture, duplicate operation IDs, or any failed required run fails closed. This diagnostic change creates no live v3 compatibility claim.

The version-3 synthetic conformance corpus contains explicit sparse, ordinary one-role, long/many-role, career-change/gap/overlap, missing-optional-field, large/long-output, ambiguous/conflicting, Unicode/non-English, adversarial, and structure-deviation classes. Each purpose receives only its allowlisted block projection. The harness executes three fresh logical operations for every applicable fixture, uses the production broker's two-call ceiling, and retains every run: primary, structural-repair, validation-repair, deterministic-fallback, safe-failure, schema-valid, evidence-valid, latency, and zero-provider-call outcomes are separate. A fallback is never provider success, and local craft evaluation proves three host-owned operations with zero provider calls. Credential-free synthetic reports carry `credential_free_synthetic` and cannot authorize provider compatibility. BrainDrive Models, OpenRouter, and Ollama evidence remain independent.

`npm run resume:quality` is the credential-free Milestone 6 quality-gate-correction harness. It runs the fixed F1–F12 synthetic fixture suite, an independent clean-text extractor, twelve mutation cases, two local clean false-blocker checks, seven persona dimensions, the F9 successor no-regression check, and an anti-overfit scan. The separate strict evaluation corpus adds nine generative fixture identities, two disjoint holdouts, must-use evidence relations, eight coverage/yield journeys, seven target classes, the frozen negative oracle, three clean positive controls, one semantic permutation relation, safe/unsafe repair relations, both successor paths, four artifact-parity mutations, and two normalized owner journeys. It checks sparse/substantive role density, confirmed support, contextual skills, summary support, chronology, padding, metric refusal, clean-text recovery, revision continuity, relation integrity, and semantic confirmation-friction limits.

The durable report binds the full Git revision plus exact quality-standard, prompt-policy, rubric, evaluator-contract, fixture-corpus, craft-report-schema, and report-schema digests. Its strict schema permits only categories, counts, statuses, and SHA-256 digests. `assertSanitizedDurableEvidence` rejects content-bearing fields, fixture canaries, and private paths. Synthetic fixtures are explicitly `workflow_only` and `higher_gate_eligible=false`; they cannot satisfy controlled generation, provider conformance, or human calibration. Deterministic success is scoped to credential-free checks: multi-run generation, provider conformance, human calibration, the numeric friction threshold, and retention/deletion remain independent mandatory gates. `release_ready` can become true only when every gate passes; an aggregate or holistic read cannot override any per-operation truth, structure, C1–C7, T1–T3, must-use, target, repair, successor, or parity failure.

`quality-evaluation.ts` defines controlled-ingestion contracts without executing controlled work. `FreshGenerationOperationSchema` requires exactly three unique operation and freshness identities for every generative fixture and owner-authorized provider/model class. Repeated or mismatched identities fail closed; every operation must independently pass its mandatory gates, so there is no best-of-three selection. `ProviderPurposeEvidenceSchema` treats timeout, response loss, refusal, malformed output, incompatibility, strict-schema failure, and unsupported claims as non-conformance. Human review requires one accepted calibration policy, attributable reviewer-identity digests for the independent resume-quality and non-technical owner roles, model/transcript/expectation/prior-score blindness, required samples, evidence-reference digests, and fail-closed shared-judgment disagreement. The accepted verification plan supplies no Spec 07 provider/model, named-reviewer, calibration, numeric-friction, or retention/deletion authority, so ordinary runs correctly report these gates as blocked.

Raw synthetic review deletion is available only through `deleteRawSyntheticReviewArtifacts` with an accepted strict retention contract, a task-selected child directory below a bounded parent, and an exact sentinel binding that directory to the contract digest. Symlinks, broad targets, missing/mismatched sentinels, and unsupported filesystem objects are rejected before deletion. The returned attestation contains only policy/content digests, counts, byte totals, completion time, and deletion status—never a path or review content. When no authorized raw workspace was created, no deletion is performed and no deletion attestation is fabricated.

The live runner is deliberately opt-in and emits only strict version-2 registry/report fields. From `builds/typescript`, an explicitly authorized operator with an isolated `PAA_MEMORY_ROOT` and already configured owner profile can run `BRAINDRIVE_RESUME_CONFORMANCE=1 npm run resume:conformance`; `BRAINDRIVE_RESUME_CONFORMANCE_PURPOSES=general_resume_draft` narrows a diagnostic run, but partial evidence cannot authorize the full corpus. `BRAINDRIVE_RESUME_CONFORMANCE_DIAGNOSTICS=1` adds only fixture/operation identity, schema/evidence booleans, disposition, and semantic code. The runner resolves credentials through the normal vault boundary and never prints them, prompts, provider errors/bodies, raw model output, endpoints, owner content, or paths. Credentialed execution is Tier C and is not part of ordinary tests.

Spec 10 also has a separately authorized, budget-bounded dense/holdout diagnostic in `scripts/resume-spec10-live-validation.ts`. It requires the exact BrainDrive Models profile/model plus explicit `BRAINDRIVE_SPEC10_LIVE_MAX_CALLS=4` and `BRAINDRIVE_SPEC10_LIVE_MAX_USD=0.5`, reads balance before and after calls, and never writes a compatibility-registry entry. The runner installs the signed Resume Builder fixture in a disposable root and sends contract-version-2 invocations through its private prepare/adjudicate MCP tools and BrainDrive's generic installed-app executor; it does not instantiate the retired Resume broker. Its strict content-free report retains only the execution-boundary identity, fixture digests, call/spend counters, completion mode, attempt count, namespaced app issue IDs, validity booleans, and statement count. It excludes prompts, prior candidates, statement identities, provider bodies, raw output, owner content, credentials, endpoints, and paths. `passed` requires both fixtures to complete from provider output; schema/evidence-valid `deterministic_fallback` is instead `recovered` with provider compatibility false. This distinction prevents successful app-owned recovery from being relabeled live-model compatibility.

The sandbox receives provider-profile and model IDs only as opaque completed-result lineage so it can persist the exact strategy/draft binding; it cannot choose or configure them. Credentials, headers, raw permissions, URLs, and paths remain excluded. The package-side MCP operations delegate to this host capability and never call a provider directly.

The isolated M6 browser journey may set `BRAINDRIVE_E2E_RESUME_INFERENCE_FIXTURE=1` through `client_web/scripts/run-isolated-e2e.mjs`. That resolver is deterministic workflow-only evidence, accepts only the structured no-tools Resume Builder call shape, and throws if asked to enter the general agent loop. It does not prove persuasive generation, provider compatibility, independent judgment, or human calibration. The flag is absent from normal runtime and Docker configuration and never adds a production compatibility entry.

`spec-09-fault-fixture.ts` is a test-import-only typed provider adapter for cross-layer recovery checks. Its exhaustive vocabulary covers clean output, structural and deterministic-validation failures, filtering/refusal/tool-call outcomes, authentication/authorization/quota/rate/deadline/network/internal failures, response loss, and compatibility/schema-support failures without inspecting owner content or fixture literals. `spec-09-integration.test.ts` applies that adapter to all twelve purposes and verifies the two-call and zero-call ceilings through the protected projection/audit boundary. The focused MCP host state-boundary case runs every terminal class, cancellation, and a recovered result against a disposable `ResumeDataStore`; it compares real pre/post reads for confirmed facts, interview/workspace, strategy, proposals, approved resume, and Career projection, observes the owner mutation methods, and permits only lifecycle-owned inference terminal/idempotency persistence. Browser fault injection is confined to Playwright request routing under the disposable isolated runner; production gateway composition does not import the fault adapter or recognize its outcomes.
