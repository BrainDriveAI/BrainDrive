# Resume Builder brokered inference

This directory is the accepted Spec 03 broker plus the Spec 06 implementation for nine Resume Builder inference purposes. Milestone 7 activates `resume_guidance` alongside the Milestone 6 revision purposes. Spec 05 M5 exposes the broker through the thin [protected app capability adapter](../app-inference/README.md). Both remain deliberately separate from `engine/loop.ts`: requests cannot discover or call tools, cannot enter the chat retry loop, and cannot select a provider, model, credential, or capability.

`ImmutableInferenceSnapshotBuilder` resolves only exact, scoped revision IDs and admits only confirmed facts. Revision classification receives one submitted revision request and its exact source definition. Revision drafting receives the same source plus the exact generating request revision; ambiguous, merely submitted, or awaiting-confirmation requests fail before provider resolution. `ResumeInferenceBroker` validates the request and every data-block digest before resolving the owner's live provider. It then uses the dedicated adapter `completeStructuredNoTools` path with `tools: []`, a fixed policy, a strict purpose schema, the accepted token/time budgets, and the caller's abort signal.

The broker never exceeds the accepted two-provider-call ceiling. Empty or schema-invalid output can use the second call for structural repair. A schema-valid result that fails deterministic validation can instead use that call for an evidence-validation repair containing only the prior structured result and safe validator findings; the model must preserve every unflagged statement exactly. If structural repair consumed the second call, a resume draft gets one local deterministic fallback that rewrites only rejected or structurally missing lines from their cited confirmed facts. The fallback makes no provider call, preserves valid statements, and must pass the same deterministic gate before completion. Auth, quota, rate-limit, policy, cancellation, network, and visible/ambiguous failures still do not fall back or retry.

Raw failed provider output is not retained or audited. Standard audit callbacks receive only opaque operation/request IDs, purpose/schema/policy IDs, model class, attempt, bounded usage availability, status, timing class, typed error code, safe validator findings on terminal rejection, and the content-free repair classification on success.

Cancellation is checked before and after provider resolution, before each bounded attempt, immediately after every provider response, and before validation/commit. A provider response that arrives after abort is projected as cancelled and cannot become a completed result. Broker idempotency hashes the immutable semantic request rather than host-generated request/timestamp fields, so a reconnect rebuild reuses the same completed operation while any snapshot, policy, schema, identity, or budget change conflicts.

The deterministic gate resolves every cited fact identity to the immutable confirmed snapshot, requires exact job source spans, validates targeted lineage, and conservatively rejects lexical/protected numeric, date, title, and URL drift. Any original or repaired result with an error finding blocks approval. M4 definitions record validator, policy, input, output, and findings digests atomically with the approved revision.

Guidance receives exactly one immutable resume definition and one deterministic quality-finding block. Results are bounded to strengths, gaps, ATS/structure observations, interview preparation, and at most three optional follow-up questions. Every item carries one of the supplied evidence labels; score, ranking, prediction, guarantee, and unsupported competence language are rejected. Malformed or unavailable provider output uses a deterministic local projection from the same finding block. It never becomes resume content and never changes approval state.

Resume-generation policy asks compatible models for a professional reverse-chronological document with a supported summary, individual job headings, job-linked responsibility and accomplishment statements, standard section identifiers, and separate education, credentials, skills, projects, volunteering, and links. Structured interview values keep a job and its accomplishments associated by an immutable fact revision, but their JSON markers and internal identities are forbidden from visible resume text. Coaching preferences can guide the draft but cannot be copied into experience. The deterministic browser fixture mirrors the section mapping, excludes preference facts from resume claims, and uses confirmed contact information for the displayed name when available.

## Compatibility gate

`ModelCompatibilityRegistry` accepts only version-1 conformance records that passed 100% schema success and the zero-unsupported-claim gate. Prompt policy version 2 changes the shared fixed policy plus `interview_assist`, `general_resume_draft`, and `targeted_resume_draft`; all prior policy-1 entries were removed. `model-compatibility.json` is intentionally empty and every live purpose now fails closed until an owner-authorized credentialed conformance run produces current per-purpose evidence. BrainDrive Models evidence would not authorize OpenRouter or Ollama identities.

`npm run resume:quality` is the credential-free Milestone 7 quality harness. It runs the fixed F1–F12 synthetic fixture suite, an independent clean-text extractor, twelve mutation cases, two clean false-blocker checks, seven persona dimensions, the F9 successor no-regression check, and an anti-overfit scan. It checks sparse/substantive role density, confirmed support, contextual skills, summary support, chronology, padding, metric pressure, clean-text recovery, and revision continuity. It emits only strict sanitized counts, outcomes, error enums, and digests; `--markdown` emits the owner-readable report form. The report scopes its pass result to credential-free deterministic checks and separately marks the required three owner-authorized generations, Tier-3 craft judging, and human calibration as awaiting evidence instead of fabricating release readiness.

The live runner is deliberately opt-in and emits only registry fields. From `builds/typescript`, an operator with an already configured owner profile can run `BRAINDRIVE_RESUME_CONFORMANCE=1 npm run resume:conformance`; `BRAINDRIVE_RESUME_CONFORMANCE_PURPOSES=general_resume_draft` narrows a rerun. `BRAINDRIVE_RESUME_CONFORMANCE_DIAGNOSTICS=1` adds only validator codes and safe messages for the synthetic corpus. The runner resolves credentials through the normal vault boundary and never prints them, prompts, provider bodies, or raw model output.

The app-visible projection reports `owner_active_compatible` as a model class and omits provider profile/model identifiers, credentials, headers, raw permissions, URLs, and paths. The package-side MCP operations delegate to this host capability and never call a provider directly.

The isolated M6 browser journey may set `BRAINDRIVE_E2E_RESUME_INFERENCE_FIXTURE=1` through `client_web/scripts/run-isolated-e2e.mjs`. That resolver is deterministic, accepts only the structured no-tools Resume Builder call shape, and throws if asked to enter the general agent loop. The flag is absent from normal runtime and Docker configuration and never adds a production compatibility entry.
