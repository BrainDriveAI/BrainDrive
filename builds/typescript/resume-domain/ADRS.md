# Resume Builder owner-data implementation decisions

Status: Accepted by DJJones, Project Owner, 2026-08-07.

Authorities: accepted Spec 2 (`/home/hex/Reference/Designs/BrainDrive-Tools/Resume-Builder/MVP/spec-02-career-facts-resume-versions-and-artifacts.md`), accepted MVP plan and Milestone 4 prompt, accepted verification plan (`/home/hex/Reference/Designs/BrainDrive-Tools/Resume-Builder/MVP/test-plan.md`), and M1 ADR-RB-003/005/018.

## ADR-RB-019 — Owner-data namespace and atomic catalog

Use the existing M2 mapping `apps/resume-builder` below the configured memory root. Immutable JSON revision files live under `records/<type>/<record-id>/<revision-id>.json`; `catalog.json` is the only visibility pointer and is atomically replaced after every referenced revision validates. The catalog carries current heads, revision locators, and completed operation outcomes. Files staged before a failed pointer swap are unreachable and therefore not domain-visible. Lifecycle code does not enumerate or remove this namespace.

This is the narrowest repository-consistent implementation of the accepted host-owned namespace plus atomic-index decision. It automatically participates in whole-memory Git history, backup restore, and migration export/import without changing those generic mechanisms.

Spec 2 Milestone 2 retains that decision and completes its transaction mechanics. A static versioned `manifest.json` declares the catalog, record, transaction, and SHA-256 integrity layout. Each revision locator binds canonical record content by digest and the catalog binds its canonical body by digest. A private `transactions/<transaction-id>` stage contains all candidate records, the complete next catalog, and a strict content-free transaction marker before any final record promotion. Exclusive promotion can create unreachable orphans, but only one verified `catalog.json` replacement can make a generation visible.

Every mutation holds both the process-local queue and a bounded `.store.lock` lease created with exclusive filesystem semantics. Version-2 leases carry an opaque lease identity, a per-runtime process-instance identity, owner PID, optional Linux process-start tick, and expiry; version-1 leases remain readable during transition. Writers reread catalog, operation, and CAS state only after acquisition, renew during work, and verify ownership immediately before switching the catalog. Live leases fail safely after the bounded wait. Expired leases, leases whose owning process is gone, and persisted leases whose PID now belongs to a different runtime instance are quarantined before reacquisition. This prevents container PID reuse from holding owner data unavailable until the full lease TTL.

Startup reconciliation treats the active verified catalog as authority. A staged transaction with its matching operation in that catalog committed before interruption and is cleaned without replay. All other stages are uncommitted; their unreferenced promoted revisions and any invalid stage/orphan are removed. Pre-switch cancellation changes no catalog generation and leaves no terminal operation entry; an equivalent retry may run. Once the catalog switches, cancellation or response loss must recover the committed identity. Git checkpointing runs after this boundary as best-effort, content-free evidence and cannot roll back or fail the domain commit.

## ADR-RB-020 — First-release migration and downgrade behavior

Version 1 is the first released Resume Builder data schema. A missing namespace initializes empty version 1 state. A pre-contract version-0 fixture exists only to exercise deterministic staging, recovery snapshot, validation, pointer commit, interruption reconciliation, and rollback. Current version-1 extensions round-trip only through explicit `extensions`; newer/unknown schema versions fail closed and remain untouched.

## ADR-RB-021 — Capability and owner-confirmation boundary

Named capability operations validate the installed grant, installation, record scopes, strict input schema, operation identity, CAS precondition, and immutable lineage before record lookup or commit. Bridge calls may read, propose, and save drafts, but app-originated booleans cannot confirm facts or approve definitions. Those transitions require the separately authenticated host-owner action path. Denials are non-enumerating and return no physical path or permission object.

## ADR-RB-022 — Career projection and return placement

Both direct and Career entry use the same deterministic projection of exactly `me/profile.md`, Career `spec.md`, and Career `plan.md`, each bounded to 16 KiB and represented by an opaque reference, kind, status, digest, timestamp, and content—never its path. Career-originated results insert one summary into Career `journal.md` through its existing anchor protocol. Direct-origin results make no Career write. A retained operation record under the app's private owner-data namespace stores only operation and before/after content digests; it makes retry and interrupted-write recovery deterministic without adding identifiers or hidden markers to the Career journal. The adapter never automatically changes profile, Career spec, or Career plan, and no starter template changes are required.

## ADR-RB-023 — M3 fact decisions, provenance, and classification

Milestone 3 retains the accepted version-1 fact/source schemas. A host-owner decision is represented in process by a non-serializable witness and stored as the exact M1 confirmation proof. The witness binds owner, actor, operation, input revision, decision, and confirmation identity; copying those fields into app/model data does not satisfy the runtime witness check. Imported/suggested facts may transition to confirmed or rejected. A confirmed fact may transition only through a material `edit_and_accept` correction. Rejected heads are terminal. Every transition creates a new revision and preserves predecessor, source, sensitivity, review, and extension data.

Grouped owner review uses one M2 catalog transaction with a CAS precondition for every fact head and a separate witness/proof per decision. Any stale head or missing/mismatched proof leaves the whole group unchanged. Equivalent terminal retries reuse the original group result and materially different input conflicts.

Proposal classification does not merge, overwrite, or reinterpret owner data. Comparisons use a normalized view only: exact values are duplicates, while structured employment values for the same employer with changed title/date fields are conflicts. The original value, state, source identities, and maximum supporting sensitivity are stored unchanged. Immutable provenance has no deletion operation in this milestone; source revisions referenced by facts remain addressable through the fact history.

M-3 continues to govern instruction overlays in the existing prompt/config path. The M3 data projection does not reinterpret instruction overlays as owner state: its allowlist remains profile, Career spec, and Career plan, and all other memory classes are excluded. M-10 profile changes remain owner-controlled proposals. M-11 Career entry uses only the accepted concise journal summary, leaving profile/spec/plan unchanged.

## ADR-RB-024 — M4 immutable resume and output lineage

Milestone 4 uses the accepted version-1 definition, job, tailored-variant, artifact, and export schemas without adding renderer, generation, chooser, transport, or lifecycle behavior. Evidence/change metadata remains embedded in the atomic tailored-variant record because that is the accepted M1 structural interface; no second evidence record class or public schema is invented.

Every catalog generation is now checked against a deterministic graph derived from all immutable revisions. Factual statements and supported evidence resolve only to confirmed fact revisions; presentation statements carry no fact links. A targeted definition has an approved general parent, one immutable job snapshot, and at least one matching variant revision. Variant selected facts and changed-statement identities must exactly match its statement/evidence support and parent comparison. Historical confirmed facts remain valid support after a later correction because the graph follows exact revision identities rather than current heads.

Comparison and selection are read-only over exact immutable definitions. Rollback creates a new definition child from the selected coherent state under CAS; targeted rollback atomically creates its matching variant and never rewrites the selected target, current baseline, job, or facts. Targeted approval likewise creates a variant for the approved successor rather than redirecting the proposal's existing variant.

Accepted artifacts bind an approved definition, its exact template versions, validation run and findings digest, renderer/font identifiers, format, and artifact digest. Export receipts require an accepted matching artifact and store only a bounded path-free destination label. Bytes and host paths remain outside owner-data records. Retirement creates a lifecycle successor only when the current revision has no inbound graph edge. Destructive deletion remains unavailable for all durable records; referenced sources, facts, definitions, jobs, variants, artifacts, and receipts therefore cannot be removed through M4 services.

## ADR-RB-025 — M5 restricted capability and owner-state boundary

The Resume Builder data router accepts only a strict projection of a consumed, one-use Spec 4/5 capability token. The projection contains opaque installation, owner, actor, app, publisher, package, grant, connection, view, operation, audience, capability, record-scope, grant-revision, revocation-generation, and expiry bindings. It deliberately excludes the bearer token, nonce, broad `ToolContext`, permission JSON, credentials, provider/model fields, and host filesystem state. Before any record lookup, the policy resolves the current lifecycle grant server-side and requires an exact live match for actor, package, installation, audience, operation, single capability, grant generation, and narrowed record scopes. Disabled, missing, revoked, expired, substituted, or widened authority therefore has no data-side effect.

The authenticated gateway owner route issues a non-serializable in-process authorization witness before `AppMcpHost` may create fact-decision evidence. This keeps gateway JWT identity and the lifecycle grant's opaque actor identity as separate accepted identity domains while preventing request data or a sandbox bridge message from manufacturing host confirmation. App-originated authority-like fields are rejected recursively, and operation lookup additionally proves the original operation's owner, actor, installation, capability, and result-record scope.

Record reads use the same `not_found_within_scope` response for an absent record, a wrong record type, and an existing record outside the grant. Stable M1 contract errors are projected with an owner-safe state; a stale revision includes only the current revision number and preserves the unsaved client proposal, while cancellation, compatibility, validation, denial, and internal failures expose no record content. M1 audit events are built from an allowlist of opaque identity, capability, outcome, revision, duration, and item-count fields, validated as content-free before reaching the logger or support bundle. The existing fixed MCP request context and generic owner authentication behavior remain unchanged.

## ADR-RB-026 — M6 deterministic migration and retained-data lifecycle

Version 1 remains the only currently readable and writable released schema. The accepted future obligation to read the immediately prior released version is not used to invent a version 2. The pre-contract version-0 fixture is migrated by one identified deterministic transformer without model input. It preserves record bytes and explicit extensions, creates an immutable migration record with source/result/transformer digests and recovery snapshot identity, validates the complete graph, and commits through one catalog replacement. The prior catalog snapshot remains recovery evidence. Every injected migration failure restores its exact bytes; a later initialize can repeat safely without duplicating a visible migration.

The verified package manifest's `compatibility.data_schema` is now an actual lifecycle gate. Install, reinstall, enable, update, rollback, and restart reconciliation validate or migrate retained data before package use. A newer retained schema blocks activation and leaves both catalog bytes and lifecycle pointer unchanged. Gateway whole-memory import/restore and lifecycle mutations share the existing migration-in-progress exclusion so neither can observe a partially replaced memory root.

The Resume Builder namespace is part of whole-memory migration archives and Git backup by physical containment, but containment alone is not validation. Migration export and remote backup validate the source graph. Migration import and backup restore validate the staged graph before replacement and the live graph before acknowledging success; their existing rollback restores the prior target on a post-replacement failure. The archive's existing encrypted-vault/master-key semantics are unchanged.

Default uninstall revokes tokens/grants and stops runtime authority in the lifecycle service, then invokes the narrow owner-data cleanup hook. That hook removes only abandoned transaction directories and unreferenced staged catalogs. It never deletes the active catalog, immutable revisions, recovery snapshots, completed operation lookup, referenced provenance, artifact/export metadata, or external owner exports. Reinstall therefore creates a fresh installation/grant and reopens the retained graph without reviving old authority. No starter-pack migration is required because M6 changes no starter default and never rewrites customized profile/Career/project files.

Logical history and explicit owner-data export are separate from path-based generic memory history. History exposes opaque revision metadata and digests only. Owner export contains the complete validated graph in a private file and returns a safe file name/count/digest receipt; migration and cleanup audit events are content-free and omit physical archive/data paths.

## ADR-RB-027 — Owner-visible interview transcript as durable provenance

DJJones approved retaining the Resume Builder interview audit trail as user-owned memory on 2026-08-10. Version 3.2.2 records the exact submitted user-visible question and answer, optional visible follow-up and outcome, topic, prompt version, session/turn identities, action, and timestamp. It does not record hidden model/system prompts, credentials, internal reasoning, unsent keystrokes, or filesystem paths. The retained transcript is evidence; the latest owner-confirmed fact revision remains operational truth.

Answered turns use the existing immutable `source` record's explicit extension namespace and are committed atomically with new fact proposals. Confirmed fact revisions already retain their source revision identities, producing the chain interview turn → proposed fact → owner decision/correction → resume statement → approved definition → artifact/export. Unchanged answers that reuse an already-confirmed fact create a durable source with an explicit confirmed-fact revision reference instead of adding a false fact. Normal skip actions commit a source turn and the corresponding progress revision in one catalog transaction. The progress record retains the opaque session identity across reloads.

This is a compatible version-1 record extension rather than a new record type or generic chat store. It uses the already-granted `career.facts.propose` and `resume.definitions.write` boundaries, remains unavailable through ordinary chat history and the app workspace projection, and participates in existing graph validation, backup/restore, migration, uninstall retention, and owner export. Capability diagnostics continue to use the content-free allowlist; transcript bodies never enter support bundles.

## ADR-RB-028 — Spec 06 schema-2 continuity and revision foundation

Status: Accepted by DJJones, Project Owner, 2026-08-10. This decision supersedes ADR-RB-020 and ADR-RB-026 only where they identify schema 1 as current.

Schema 2 is the active Resume Builder owner-data schema. Current packages read schemas 1–2 and write only schema 2. Startup performs the retained deterministic 0→1 transformation and then a deterministic, no-model 1→2 transformation. The second step preserves every existing record file, revision locator, content digest, operation, and explicit extension; adds only a migration revision with safe provenance; validates a fully staged catalog; and atomically switches the catalog pointer. Recovery snapshots and versioned or legacy transaction markers make every injected interruption restartable. Unknown schema 3 state is inspected but never rewritten, and a schema-1-only package cannot activate after schema-2 data exists.

Schema 2 adds exact interview recovery state, structured job-evidence facts, durable revision requests and outcomes, explicit successor context, strict definition comparison/impact/guidance results, and lineage/retention/export coverage for the new revision record. These shapes reuse strict discriminators under the existing eleven data capabilities. Fact confirmation and definition approval still require their non-serializable host witnesses; app data cannot manufacture either transition.

The three added inference purposes are contract-only and no-tools: `resume_revision_classify`, `resume_revision_draft`, and `resume_guidance`. They have bounded result schemas and purpose ceilings but no accepted provider compatibility records. The credential-free quality harness loads only fixed synthetic fixtures, uses an independent logical-line extractor boundary, rejects fixture-literal coupling in product code/policy, and emits a sanitized schema-valid report. This milestone activates no recovery, job-interview, remembered-detail, comparison, revision, guidance, clean-text, Copy, or text-export UI and does not enforce quality at runtime.

That activation statement records the Milestone 1 foundation decision. Later milestone ADRs activate only their named slices; ADR-RB-033 activates natural-language revision while guidance, clean text, Copy, text export, and final quality enforcement remain inactive.

## ADR-RB-029 — Exact-slot recovery is an acknowledged owner-data transaction

**Decision:** Recovery remains one optional field on the schema-2 interview-progress head, keyed by the exact session, confirmed employment revision or null, question, and input field. The host owns its timestamp and acknowledged revision. A value is saved only after the atomic catalog acknowledges the same digest. Saves use CAS plus deterministic operation identity; response loss is reconciled through the existing installation-scoped operation journal. Conflict retains both values until the owner selects local, saved, or discard. Discard removes only the recovery value. Submit atomically clears it and links one visible interview-turn source to the confirmed-fact path.

**Reason:** Browser storage or optimistic status could claim durability that did not happen, while writing unsent text into fact provenance, inference, Career, or logs would promote draft content across authority boundaries. Reusing the catalog transaction, operation journal, strict lineage, and retained lifecycle preserves exact content through restart/reinstall without inventing another store or weakening confirmation.

## ADR-RB-030 — Job evidence is explicit, optional, and employment-revision exact

**Decision:** The active interview considers six deterministic evidence dimensions for one confirmed employment revision at a time. Existing confirmed context satisfies dimensions before questioning. Each submitted outcome is a schema-validated `job_evidence` fact with either one exact employment revision or an explicit general association, and normal host confirmation remains mandatory. Skip, unknown, not-applicable, and complete-for-now are durable outcomes but never resume claims. The exact job and dimension survive recovery, pause, restart, Back, review, and reopen.

Model assistance is limited to one active-job question with no tools and fails closed without current compatibility evidence. Content-free diagnostics allow only opaque job revision, dimension enum, deterministic or broker-ranked method, outcome enum, and safe error metadata. Generation may use answered evidence only, keeps sparse or older roles short, avoids padding and metric pressure, and contextualizes tools only when confirmed support exists.

## ADR-RB-031 — Remembered details create one immutable proposal and derived impact

**Decision:** A returning owner may select an exact confirmed employment revision or use normalized exact matching against the owner-visible job label. No match and multiple matches are read-only states. Exact duplicate content records the visible owner action against the existing confirmed fact and performs neither confirmation nor generation. New and corrected content continues through the existing host-witnessed fact transitions.

After confirmation, generation receives the exact current confirmed-fact revisions. The resulting definition is proposed, general, parented to the selected approved source, and records the changed fact revisions plus the exact derived stale tailored variants. Equivalent retries converge on one successor even under a new transport operation. The domain rejects changed identities for semantically unchanged predecessor statements and rejects an unchanged resume result.

Impact is not stored as mutable status. It is derived from fact supersession, statement support, the actual source/successor diff, tailored parent lineage, and tailored evidence links. Historical approved definitions and variants remain byte-identical. Career continues to read only the latest approved general definition, so confirmation, generation failure, retry, and proposal do not publish; later host approval is the only publication boundary.

## ADR-RB-032 — Version comparison is deterministic, exact, and read-only

**Decision:** History comparison selects exactly two immutable definition revisions and executes as the `compare_definitions` discriminator of `resume.definitions.read`. Authorization precedes input parsing and lookup. The service compares the requested revisions—not current heads or substitutes—and checks optional expected revision numbers. Prior-revision and parent-definition edges form an undirected reachability graph so adjacent and non-adjacent successors are related. Comparable definitions have the same kind; targeted definitions also name the same exact job revision. Unrelated or incompatible selections return a bounded unavailable result with no statement manifest.

Available results classify stable statement identities independently as added, removed, semantic-content changed, moved, evidence-reference changed, or unchanged. Semantic comparison excludes support references and position, making support-only changes evidence changes and permitting movement to coexist with content change. Entries retain deterministic before/after snapshots and digests for the owner surface, while the audit event retains only selected opaque revision IDs, definition digests, relation/result enums, class counts, duration, outcome, and safe error code.

**Reason:** A model-generated explanation or comparison of current heads could vary, expose more data than selected, or silently compare the wrong versions. A pure manifest over immutable records is reproducible, testable across ordering seeds, and demonstrably non-mutating. Keeping the operation inside the existing read capability prevents new authority and guarantees no definition/fact/Career write, commit, provider call, rollback, guidance, revision, clean-text, Copy, or export behavior is activated by this milestone.

## ADR-RB-033 — Natural-language revision is scoped, immutable, and separately approved

**Decision:** Persist an owner revision request against one exact approved general or targeted definition and one validated resume, section, or statement target before inference. Classification is immutable. Presentation requests may generate immediately; factual and mixed requests require a host-issued owner confirmation; ambiguous requests stop at clarification and cannot produce a proposal. Generation receives the exact source and generating request revisions, has at most two attempts, and commits the validated proposed definition, targeted variant when applicable, and request outcome in one catalog transaction. Unchanged statements keep stable identities, changes must stay inside the declared scope, and every factual claim must retain confirmed support. Accept, owner Edit, Reject, and Regenerate require separate host owner actions and create immutable request successors. Accepting or editing never approves the definition; the existing definition-approval witness remains mandatory.

**Reason:** Treating free-form text as direct mutation or authority would let prompt content bypass fact confirmation, approval, and lineage. Exact persisted inputs plus deterministic validation make retry, cancellation, history, export, reinstall, and audit behavior reproducible while keeping source definitions and sibling variants immutable. The M6 credential-free pairwise fixture guards preservation, declared rewriting, structure, support, repetition, and generic-language regressions; it is current milestone evidence, not the later final-quality release gate.

## ADR-RB-034 — Schema-3 migration separates factual evidence from coverage dispositions

Status: Proposed for review under draft Spec 07; not accepted product authority.

Schema 3 is write-current and schemas 2–3 are package-readable. The retained startup chain can still consume schema 0/1 only to migrate it forward. The 2→3 transformer preserves historical revision bytes and extensions, creates deterministic per-employment coverage heads, and never rewrites an old non-fact job-evidence record into a fact. New schema-3 job-evidence career records may contain answered owner evidence only; unknown, N/A, skipped, deferred, and conflicting states belong to the coverage record. New immutable inference snapshots filter every legacy non-answered job-evidence revision from both factual blocks and their revision manifest.

The migration remains snapshot-backed, staged, atomic, restart-safe, and fault-injected at the existing five boundaries. Schema-3-only writes make downgrade a refusal, not a destructive reverse transformation. The retained schema-2 snapshot and owner export are the recovery mechanisms. This decision adds contract and migration behavior only; ranked opportunities, grouped confirmation, strategy execution, target gating, craft evaluation/repair, approval enforcement, UI projection, and artifact parity execution remain owned by later milestones.

## ADR-RB-035 — Coverage is explicit and opportunity selection is deterministic

Status: Proposed for review under draft Spec 07; not accepted product authority.

Each confirmed employment revision owns one CAS-guarded schema-3 coverage head with six explicit dimension states. The host initializes it from exact confirmed evidence only. Unknown, not-applicable, skipped, deferred, conflicting, and metric refusal are coverage/opportunity transitions, never career facts. Complete-for-now changes every remaining unanswered dimension in one immutable successor. Owner reopen changes only the selected dimension or stored opportunity and preserves all confirmed evidence.

The package ranks strategy-neutral opportunity categories deterministically, with distinct qualitative and optional metric identities. Presentation is durably counted before display; a declined or completed equivalent is suppressed for the same confirmed context, survives restart, and re-enters only after explicit reopen or a different confirmed context. Interview inference uses version-2 input/output binding and may phrase but never select or mutate the opportunity identity. One submitted answer is split into bounded owner-visible factual units and reviewed in one atomic host group, with an independently witnessed accept/reject decision per unit. Only confirmed units become factual coverage. Audit events remain strict and content-free. Strategy execution and all Spec 07 M3+ behavior remain dormant.
