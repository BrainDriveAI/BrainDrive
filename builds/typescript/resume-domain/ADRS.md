# Resume Builder owner-data implementation decisions

Status: Accepted by DJJones, Project Owner, 2026-08-07.

Authorities: accepted Spec 2 (`/home/hex/Reference/Designs/BrainDrive-Tools/Resume-Builder/MVP/spec-02-career-facts-resume-versions-and-artifacts.md`), accepted MVP plan and Milestone 4 prompt, accepted verification plan (`/home/hex/Reference/Designs/BrainDrive-Tools/Resume-Builder/MVP/test-plan.md`), and M1 ADR-RB-003/005/018.

## ADR-RB-019 — Owner-data namespace and atomic catalog

Use the existing M2 mapping `apps/resume-builder` below the configured memory root. Immutable JSON revision files live under `records/<type>/<record-id>/<revision-id>.json`; `catalog.json` is the only visibility pointer and is atomically replaced after every referenced revision validates. The catalog carries current heads, revision locators, and completed operation outcomes. Files staged before a failed pointer swap are unreachable and therefore not domain-visible. Lifecycle code does not enumerate or remove this namespace.

This is the narrowest repository-consistent implementation of the accepted host-owned namespace plus atomic-index decision. It automatically participates in whole-memory Git history, backup restore, and migration export/import without changing those generic mechanisms.

Spec 2 Milestone 2 retains that decision and completes its transaction mechanics. A static versioned `manifest.json` declares the catalog, record, transaction, and SHA-256 integrity layout. Each revision locator binds canonical record content by digest and the catalog binds its canonical body by digest. A private `transactions/<transaction-id>` stage contains all candidate records, the complete next catalog, and a strict content-free transaction marker before any final record promotion. Exclusive promotion can create unreachable orphans, but only one verified `catalog.json` replacement can make a generation visible.

Every mutation holds both the process-local queue and a bounded `.store.lock` lease created with exclusive filesystem semantics. The lease carries an opaque identity, owner process, and expiry; writers reread catalog, operation, and CAS state only after acquisition, renew during work, and verify ownership immediately before switching the catalog. Live leases fail safely after the bounded wait. Expired leases and leases whose owning process is gone are quarantined before reacquisition.

Startup reconciliation treats the active verified catalog as authority. A staged transaction with its matching operation in that catalog committed before interruption and is cleaned without replay. All other stages are uncommitted; their unreferenced promoted revisions and any invalid stage/orphan are removed. Pre-switch cancellation changes no catalog generation and leaves no terminal operation entry; an equivalent retry may run. Once the catalog switches, cancellation or response loss must recover the committed identity. Git checkpointing runs after this boundary as best-effort, content-free evidence and cannot roll back or fail the domain commit.

## ADR-RB-020 — First-release migration and downgrade behavior

Version 1 is the first released Resume Builder data schema. A missing namespace initializes empty version 1 state. A pre-contract version-0 fixture exists only to exercise deterministic staging, recovery snapshot, validation, pointer commit, interruption reconciliation, and rollback. Current version-1 extensions round-trip only through explicit `extensions`; newer/unknown schema versions fail closed and remain untouched.

## ADR-RB-021 — Capability and owner-confirmation boundary

Named capability operations validate the installed grant, installation, record scopes, strict input schema, operation identity, CAS precondition, and immutable lineage before record lookup or commit. Bridge calls may read, propose, and save drafts, but app-originated booleans cannot confirm facts or approve definitions. Those transitions require the separately authenticated host-owner action path. Denials are non-enumerating and return no physical path or permission object.

## ADR-RB-022 — Career projection and return placement

Both direct and Career entry use the same deterministic projection of exactly `me/profile.md`, Career `spec.md`, and Career `plan.md`, each bounded to 16 KiB and represented by an opaque reference, kind, status, digest, timestamp, and content—never its path. Career-originated results insert one summary into Career `journal.md` through its existing anchor protocol. Direct-origin results make no Career write. A retained operation record under the app's private owner-data namespace stores only operation and before/after content digests; it makes retry and interrupted-write recovery deterministic without adding identifiers or hidden markers to the Career journal. The adapter never automatically changes profile, Career spec, or Career plan, and no starter template changes are required.

## ADR-RB-023 — M3 fact decisions, provenance, and classification

Milestone 3 retains the accepted version-1 fact/source schemas. A host-owner decision is represented in process by a non-serializable witness and stored as the exact M1 confirmation proof. The witness binds owner, actor, operation, input revision, decision, and confirmation identity; copying those fields into app/model data does not satisfy the runtime witness check. Imported/suggested facts may transition to confirmed or rejected. A confirmed fact may transition only through a material `edit_and_accept` correction. Rejected heads are terminal. Every transition creates a new revision and preserves predecessor, source, sensitivity, review, and extension data.

Grouped owner review uses one M2 catalog transaction with a CAS precondition for every fact head and a separate witness/proof per decision. Any stale head or missing/mismatched proof leaves the whole group unchanged. Equivalent terminal retries reuse the original group result and materially different input conflicts.

Proposal classification does not merge, overwrite, or reinterpret owner data. Comparisons use a normalized view only: exact values are duplicates, while structured employment values for the same employer with changed title/date fields are conflicts. The original value, state, source identities, and maximum supporting sensitivity are stored unchanged. Immutable provenance has no deletion operation in this milestone; source revisions referenced by facts remain addressable through the fact history.

M-3 continues to govern instruction overlays in the existing prompt/config path. The M3 data projection does not reinterpret instruction overlays as owner state: its allowlist remains profile, Career spec, and Career plan, and all other memory classes are excluded. M-10 profile changes remain owner-controlled proposals. M-11 Career entry uses only the accepted concise journal summary, leaving profile/spec/plan unchanged.

## ADR-RB-024 — M4 immutable resume and output lineage

Milestone 4 uses the accepted version-1 definition, job, tailored-variant, artifact, and export schemas without adding renderer, generation, chooser, transport, or lifecycle behavior. Evidence/change metadata remains embedded in the atomic tailored-variant record because that is the accepted M1 structural interface; no second evidence record class or public schema is invented.

Every catalog generation is now checked against a deterministic graph derived from all immutable revisions. Factual statements and supported evidence resolve only to confirmed fact revisions; presentation statements carry no fact links. A targeted definition has an approved general parent, one immutable job snapshot, and at least one matching variant revision. Variant selected facts and changed-statement identities must exactly match its statement/evidence support and parent comparison. Historical confirmed facts remain valid support after a later correction because the graph follows exact revision identities rather than current heads.

Comparison and selection are read-only over exact immutable definitions. Rollback creates a new definition child from the selected coherent state under CAS; targeted rollback atomically creates its matching variant and never rewrites the selected target, current baseline, job, or facts. Targeted approval likewise creates a variant for the approved successor rather than redirecting the proposal's existing variant.

Accepted artifacts bind an approved definition, its exact template versions, validation run and findings digest, renderer/font identifiers, format, and artifact digest. Export receipts require an accepted matching artifact and store only a bounded path-free destination label. Bytes and host paths remain outside owner-data records. Retirement creates a lifecycle successor only when the current revision has no inbound graph edge. Destructive deletion remains unavailable for all durable records; referenced sources, facts, definitions, jobs, variants, artifacts, and receipts therefore cannot be removed through M4 services.

## ADR-RB-025 — M5 restricted capability and owner-state boundary

The Resume Builder data router accepts only a strict projection of a consumed, one-use Spec 4/5 capability token. The projection contains opaque installation, owner, actor, app, publisher, package, grant, connection, view, operation, audience, capability, record-scope, grant-revision, revocation-generation, and expiry bindings. It deliberately excludes the bearer token, nonce, broad `ToolContext`, permission JSON, credentials, provider/model fields, and host filesystem state. Before any record lookup, the policy resolves the current lifecycle grant server-side and requires an exact live match for actor, package, installation, audience, operation, single capability, grant generation, and narrowed record scopes. Disabled, missing, revoked, expired, substituted, or widened authority therefore has no data-side effect.

The authenticated gateway owner route issues a non-serializable in-process authorization witness before `AppMcpHost` may create fact-decision evidence. This keeps gateway JWT identity and the lifecycle grant's opaque actor identity as separate accepted identity domains while preventing request data or a sandbox bridge message from manufacturing host confirmation. App-originated authority-like fields are rejected recursively, and operation lookup additionally proves the original operation's owner, actor, installation, capability, and result-record scope.

Record reads use the same `not_found_within_scope` response for an absent record, a wrong record type, and an existing record outside the grant. Stable M1 contract errors are projected with an owner-safe state; a stale revision includes only the current revision number and preserves the unsaved client proposal, while cancellation, compatibility, validation, denial, and internal failures expose no record content. M1 audit events are built from an allowlist of opaque identity, capability, outcome, revision, duration, and item-count fields, validated as content-free before reaching the logger or support bundle. The existing fixed MCP request context and generic owner authentication behavior remain unchanged.

## ADR-RB-026 — M6 deterministic migration and retained-data lifecycle

Version 1 remains the only currently readable and writable released schema. The accepted future obligation to read the immediately prior released version is not used to invent a version 2. The pre-contract version-0 fixture is migrated by one identified deterministic transformer without model input. It preserves record bytes and explicit extensions, creates an immutable migration record with source/result/transformer digests and recovery snapshot identity, validates the complete graph, and commits through one catalog replacement. The prior catalog snapshot remains recovery evidence. Every injected migration failure restores its exact bytes; a later initialize can repeat safely without duplicating a visible migration.

The verified package manifest's `compatibility.data_schema` is now an actual lifecycle gate. Install, reinstall, enable, update, rollback, and restart reconciliation validate or migrate retained data before package use. A newer retained schema blocks activation and leaves both catalog bytes and lifecycle pointer unchanged. Gateway whole-memory import/restore and lifecycle mutations share the existing migration-in-progress exclusion so neither can observe a partially replaced memory root.

The Resume Builder namespace is part of whole-memory migration archives and Git backup by physical containment, but containment alone is not validation. Migration export and remote backup validate the source graph. Migration import and backup restore validate the staged graph before replacement and the live graph before acknowledging success; their existing rollback restores the prior target on a post-replacement failure. The archive's existing encrypted-vault/master-key semantics are unchanged.

Default uninstall revokes tokens/grants and stops runtime authority in the lifecycle service, then invokes the narrow owner-data cleanup hook. That hook removes only abandoned transaction directories and unreferenced staged catalogs. It never deletes the active catalog, immutable revisions, recovery snapshots, completed operation lookup, referenced provenance, artifact/export metadata, or external owner exports. Reinstall therefore creates a fresh installation/grant and reopens the retained graph without reviving old authority. No starter-pack migration is required because M6 changes no starter default and never rewrites customized profile/Career/project files.

Logical history and explicit owner-data export are separate from path-based generic memory history. History exposes opaque revision metadata and digests only. Owner export contains the complete validated graph in a private file and returns a safe file name/count/digest receipt; migration and cleanup audit events are content-free and omit physical archive/data paths.
