# Resume Builder owner-data domain

This directory implements the Spec 2 owner-data milestones, Spec 06 through Milestone 8, and the accepted Spec 07 quality-gate-correction work through Milestone 7. The correction advances owner data to schema 4, canonicalizes strategy inputs, activates evidence-cited craft report v2 and one pure quality-state adjudicator, derives exactly one bounded correction action, and preserves all earlier reports as historical pre-correction evidence. Milestone 5 exposes that domain projection to the owner surface and carries exact approved identity plus narrow quality metadata through Career return and read-only publication without changing resume content. Milestones 6–7 add the credential-free correction harness and the fail-closed integration record; they do not activate controlled provider runs, human review, numeric friction, final target thresholds, or release acceptance. RB7-OQ-1 is implemented exactly as an approval/release blocker for `evidence_limited`; RB7-OQ-2 through RB7-OQ-4 remain accepted implementation blockers, not product defaults. The correction's local evidence and mandatory immutable-candidate/provider/human/Docker/native blockers are recorded in [`SPEC-07-QGC-M7-ACCEPTANCE.md`](SPEC-07-QGC-M7-ACCEPTANCE.md). Milestone 8's accepted Spec 06 requirement matrix remains recorded in [`SPEC-06-M8-ACCEPTANCE.md`](SPEC-06-M8-ACCEPTANCE.md).

The physical namespace is `apps/resume-builder` below the configured memory root. App callers receive only opaque record/revision/operation identities and bounded record views. They never receive this path, a memory root, generic file operations, provider credentials, or internal permission objects.

Provider inference and wording generation remain in the separate host broker; this directory never resolves a model or credential. Rendering and browser save remain in the separate host broker and web owner surface. This domain only validates and records artifact/export lineage and performs no direct filesystem export, Docker supervision change, or desktop behavior.

Career return placement requires an operation UUID. For summary v2, the capability verifies the exact approved definition or targeted variant identity, definition digest, narrow state, and current report reference/digest against durable records before placement. Its private operation record captures canonical input plus before/after digests so the same deterministic retry can distinguish not-written from committed state without putting operation IDs, digests, or paths into the owner-facing Career journal.

Career's readable `General Resume` document is separate from that narrow journal return. The gateway's generic published-document provider tries approved general definitions newest-first, validates current report evidence and artifact parity, renders a bounded Markdown projection, and refreshes it through the normal Career document tree before listing or reading. It publishes the narrow quality state as optional metadata beside—never inside—the exact Markdown. A failed latest candidate falls back to the newest verifiable prior approval. The immutable approved definition remains authoritative; this domain does not write the project file or grant the installed app filesystem access.

## Scoped capability service

The installed Resume Builder reaches this domain through exactly eleven data operations: `career.context.read`, `career.facts.read`, `career.facts.propose`, `career.facts.confirm`, `resume.definitions.read`, `resume.definitions.write`, `resume.jobs.read`, `resume.jobs.write`, `resume.artifacts.register`, `resume.export.request`, and `resume.operations.read`. `app.inference.request` remains a separate no-tools host broker and is rejected by the data router.

Each call carries a host-created restricted authority projection derived from a consumed one-use app token. The router revalidates it against the current lifecycle grant before parsing or locating records, then narrows the internal grant to one capability and the token's record scopes. Authority, confirmation, operation, schema/migration, provider/model, permission, and installation fields in app input are rejected. Inputs are bounded to 256 KiB. Operation reads are restricted to the same owner, actor, installation, original capability grant, and result-record scope. Missing, wrong-type, and out-of-scope record probes all return the same `not_found_within_scope` response.

Authenticated owner actions use `POST /apps/resume-builder/data/call`. A successful call returns `{ result }`. A failure returns the M1 `{ error, owner_state }` contract: only a stale-revision conflict includes `current_revision`, sets `refresh_required`, and records that the unsaved proposal is preserved. Other denial, cancellation, compatibility, validation, idempotency, and recoverable failures use stable safe messages with no record content, permission object, credential, destination, or path. Capability audit events are schema-validated and content-free before logging; the same allowlisted event is safe when copied into a support bundle.

## Career facts and sources

App/model input can create only `imported` or `suggested` facts. Confirmation, correction, and rejection require a non-serializable host-issued owner-decision witness bound to the owner, actor, operation, input revision, and individual decision. Group review remains one atomic M2 catalog transaction but carries one independently validated witness and immutable successor per fact. Rejected facts and all predecessor revisions remain available for review history; confirmed corrections point to the exact revision they supersede and preserve source references and the most restrictive inherited sensitivity.

Proposal classification is advisory and durable in the fact extension: exact normalized matches are `duplicate`; structured employment proposals for the same employer with different title or date fields are `conflict`; stored owner text, proposal state, provenance, and sensitivity are never normalized away. Non-interview sources contain an owner-readable safe label, capture metadata, digest, opaque reference, sensitivity, and an untrusted-data marker—not a source body or host path. An `owner_interview` source may additionally carry the validated `interview_turn` audit extension: the exact submitted user-visible question and answer, optional visible follow-up and outcome, topic, prompt version, session/turn identities, action, and timestamp. It never contains hidden model/system prompts, credentials, filesystem paths, or unsent textarea contents.

Answered turns are committed with the source and proposed fact, so every accepted or corrected fact retains its exact source revision. When unchanged wording reuses an already-confirmed fact, a durable turn source records that fact revision explicitly without creating a false duplicate fact. A normal skipped-topic transition commits the skipped turn and progress revision atomically. These audit records are retained for owner history/export but are not returned as ordinary BrainDrive chat history or exposed in the Resume Builder workspace view.

Schema-3 coverage has one deterministic head per confirmed employment revision and six explicit dimensions. Initialization derives only already-confirmed exact-job evidence. CAS-guarded transitions record answered, unknown, not-applicable, skipped, conflicting, deferred, and owner-reopened states without turning a non-fact disposition into a career fact. Complete-for-now changes all remaining unanswered dimensions in one catalog revision. Each opportunity stores its subtype, strategy-neutral value category, context digest, one-attempt state, suppression reason, and reopen time. Answered coverage validates every cited confirmed job-evidence revision against the same employment revision and dimension. Content-free diagnostics expose only opaque identities, state/method enums, attempt/group/unit/yield counts, safe timing classes, and safe errors.

A persisted `resume_strategy` is derived planning data, never a career fact or owner score. Its input digest binds the exact canonical current confirmed-fact and coverage heads, deterministic evidence annotations, presentation preferences, prompt policy 8, accepted quality-standard revision 3, and one owner-active provider/model identity. General definitions produced under that policy carry the strategy revision and all input/output digests. Every strategy must-use identity must appear in statement lineage or one visible allowed omission. Approval rechecks current heads and fails closed after a fact or coverage change; historical approved definitions remain immutable.

A persisted `target_fit_analysis` binds that approved general revision and strategy to the exact confirmed-fact snapshot, immutable job content digest, evidence-matrix digest, prompt/provider/model input and output digests, and a versioned threshold policy. The current threshold is explicitly provisional pending RB7-OQ-3 acceptance. A failed gate is a completed durable no-change record with a bounded reason and owner actions to use the general resume, answer optional evidence questions when useful, or try another target. A passing record is single-use: targeted generation must cite it, apply exactly its supported material-change manifest, and atomically create one child, one tailored variant, and the completed analysis successor under CAS. Retries reuse the same semantic operation; a stale parent, target, strategy, fact snapshot, or consumed analysis fails closed. No score, hiring prediction, target-text keyword injection, or general-parent mutation is stored.

`career.context.read` projects exactly owner profile, Career spec, and Career plan. Each result is bounded to 16 KiB, uses a stable opaque reference, and reports present/missing state, digest, and modification time without a path. Instruction bases/overlays, journals, conversations, unrelated projects, and search are excluded. Direct entry makes no Career write. Career entry inserts only the versioned M-11 return summary; profile, Career spec, and Career plan remain byte-unchanged proposals/parent state.

## Resume, job, artifact, and export lineage

Every catalog read and commit derives and validates a graph across all immutable revisions. General definitions distinguish factual statements from presentation-only text, and their selected fact snapshot exactly matches factual support. Targeted definitions add one approved general parent and one immutable untrusted job snapshot; the atomic tailored-variant record holds the accepted evidence matrix and exact changed-statement identities. All selected or evidence-linked facts must resolve to confirmed revisions, including historical confirmed revisions superseded by later corrections.

Definition comparison accepts two exact immutable revision identities plus optional expected revisions through `resume.definitions.read`. It authorizes before lookup, traverses prior/parent lineage for adjacent or non-adjacent relationships, and fails safely for missing, stale, unrelated, or incompatible kind/job-target selections without substituting another version. Available results deterministically report added, removed, semantic-text changed, moved, evidence-reference changed, and unchanged statements in stable order, alongside relation, compatibility, input digests, aggregate evidence changes, and count-only summaries. Support-only differences are evidence changes rather than text changes. The operation performs no model call, commit, Career write, or record mutation; its content-free diagnostic contains only opaque revision IDs, digests, relation/result enums, counts, duration, and safe errors. Selection returns an exact immutable revision. Rollback creates a new coherent child under CAS; a targeted rollback or approval creates its matching variant in the same M2 catalog transaction. Retirement is an immutable lifecycle successor and is allowed only without inbound references. Destructive deletion of durable records is intentionally unavailable.

Remembered-job matching is read-only. An explicit confirmed employment revision wins; otherwise only a normalized exact owner-visible `title at employer` label can match. Zero matches return explicit owner choices, and multiple exact matches return candidates without a write. After normal witnessed fact confirmation, a remembered successor must be one proposed general definition parented to the exact approved source. Its current changed-fact revisions and derived stale-variant identities are validated, an equivalent retry reuses the existing successor, unchanged predecessor statements retain their IDs, and a semantically unchanged proposal is rejected.

Impact analysis follows each current changed fact through its immutable supersession chain, compares the actual source/successor statements, and reports added, removed, corrected, and reworded identities in source order followed by additions. Tailored variants are never mutated: direct children of the source, or variants whose evidence links to the changed lineage, are derived as `based_on_older_evidence` with `explicit_owner_action` rebuild semantics. Content-free match, successor, and impact diagnostics contain only enum outcomes, opaque revisions, counts, duration, and safe errors.

Natural-language revision begins with a durable request bound to one exact immutable source definition and a validated resume, section, or statement target. Classification is immutable once recorded: presentation-only requests may enter generation, factual and mixed requests require a host-issued owner confirmation before generation, and ambiguous requests retain a clarification prompt without a proposal. The generating request revision and approved source remain unchanged while a proposal is built atomically as a new proposed definition (and matching targeted variant where applicable). The validator rejects target drift, changed identities outside scope, unsupported factual inflation, and structural loss; unchanged statements retain stable identities. Accept, owner Edit, Reject, and Regenerate are witnessed request-state successors. None approves the definition: approval remains the existing separate host decision. Retry is bounded to two generation attempts, cancellation/failure retains the request, and active-version selection excludes rejected and regenerate outcomes.

Revision lineage is request → classified/confirmed generating request → proposed definition, with the proposal also deriving from the exact source definition. Owner Edit creates a separate validated immutable proposal while retaining the generating instruction identity. Export, backup/restore, migration, history, default uninstall/reinstall, and graph validation retain the request and successor edges. Normal diagnostics expose only opaque identities, enums, counts, attempts, digests, durations, and safe errors; request text and resume content remain private owner data.

Historical schema-3 approval behavior recomputes the deterministic quality gate and uses craft report v1. Under schema 4 that evidence remains readable but is classified as `pre_correction_review`; it does not prove a corrected product-craft pass. Corrected approval evidence v2 requires an exact current craft report v2 and product evaluator binding. Report v2 requires all ten criterion verdicts with bound positive, negative, or explicit-absence evidence, immutable definition/strategy/fact/coverage/quality identities, independently extracted anchor identities, score-free findings, and a body digest. `adjudicateResumeQualityState` is the shared projection used by report persistence and approval: unavailable, malformed, incompatible, disputed, or stale review is incomplete; mandatory failure needs correction; accepted evidence-limited review remains non-passing; and only a complete standard-context pass can become owner-approved. Milestone 4 derives one of `repair_statement`, `add_evidence`, `manual_revision`, or `keep_prior_or_exit`. Statement repair is one same-provider/model attempt against exact negative statement evidence and one correction class; it preserves title, section and statement order, statement shape, support, and unflagged statements, then reruns truth, structure, mechanical, anchor, and every craft criterion before atomically storing a proposed successor plus report v2. Rejection/failure stores no successor. Explicit absence may return one current bound coverage opportunity but creates no fact; normal witnessed confirmation and a new strategy/proposal/report remain separate operations. Artifact registration, rendering, export, and Career projection continue to fail closed against the approval contract they consume.

Accepted PDF or text artifact metadata must match the approved definition's template and deterministic validation identity/findings digest and retains renderer, font-manifest, format, MIME, and artifact digests. Artifact bytes remain outside the record store. Export receipts require a matching accepted artifact and retain only the safe destination label and outcome, never a host path.

The host-managed Career Markdown projection is not an artifact record or export receipt. It is a readable, read-only view of the latest approved general definition, regenerated on project access so a newer approved definition cannot leave Career displaying an older resume.

## Durable record matrix

| Record | Authority and lineage | Retention |
|---|---|---|
| source / interview turn / career fact | Source digest and immutable source revision; owner-interview sources retain submitted visible turns; only a host-mediated owner proof creates a confirmed fact revision | durable provenance or durable interview audit / durable owner data |
| resume definition / tailored variant | Exact confirmed fact revisions; general predecessor or general parent plus immutable job revision; approved revisions atomically carry validator/policy/input/output/findings digests | durable owner data |
| job description | Owner-pasted text stored as untrusted immutable data with a verified digest | durable provenance while referenced |
| artifact / export receipt | Definition, validator, renderer, template, font, artifact, operation, and safe destination metadata only | durable owner data |
| interview progress | CAS-protected exact session/job/question/field recovery value, server acknowledgement, stable interview-session identity, last submitted turn, and topic progress | durable owner data |
| revision request | Exact immutable source/target identities, request digest, bounded classification/outcome state, and resulting successor identity | durable owner data |
| migration | Source/result digests and recovery snapshot identity | rollback recovery window |

Every durable mutation uses an operation UUID, canonical input digest, installation identity, named capability, and expected revision where an existing record is updated. Equivalent retries reuse the committed revisions; mismatched input conflicts. The catalog pointer is the visibility boundary for multi-record commits.

## Atomic store and recovery

`manifest.json` fixes the version-1 store layout and integrity mode. `catalog.json` remains the only active-generation pointer. A commit writes canonical immutable revisions and the complete next catalog below a private transaction directory, verifies their digests and references, promotes revisions with exclusive-create semantics, then atomically replaces `catalog.json`. Git history is attempted afterward as best-effort evidence and cannot change the domain outcome.

Writers serialize in-process and acquire a bounded cross-process lease before rereading the active catalog, operation journal, and CAS precondition. A live lease returns a content-free retryable failure after the wait bound. Version-2 leases bind the PID to a process-instance UUID and, on Linux, the kernel process start tick. An expired lease, a lease owned by a process that no longer exists, or a persisted lease whose PID was reused by a restarted container/process is quarantined and reclaimed. Version-1 leases remain readable for compatibility. Lease identity and expiry are rechecked immediately before the catalog switch.

Startup reconciliation runs under the same lease. A transaction whose operation is present in the verified active catalog is already committed and only its private stage is removed. Every other stage is uncommitted; promoted files not referenced by the active catalog and all invalid/incomplete stages are removed. Readers never enumerate transaction directories or orphan revisions. A missing initial catalog creates empty generation zero; malformed manifests/catalogs, digest failures, missing revisions, locator/reference mismatches, and newer schemas fail closed without replacing the retained state.

Cancellation before the pointer switch removes staged/promoted artifacts and leaves both generation and operation visibility unchanged. Cancellation or response loss after the switch returns or recovers the committed operation identity. Store errors and the optional Git-checkpoint diagnostic contain only stable error categories—never record content or physical paths.

## Exact-slot interview recovery

`interview_recovery_save` is the only draft-save transition. The server verifies the exact value digest and session/job/question/field slot, validates any job slot as a confirmed same-owner employment fact, assigns the save time and acknowledged progress revision, and commits through the atomic catalog. The UI displays `Saved` only for that acknowledged digest. It waits 1.5 seconds after editing, flushes on submit/Pause/Continue, cancels timers on slot or resource teardown, and uses a deterministic semantic operation identity for retries.

Bridge message IDs remain unique transport replay identities. A separate optional `request_operation_id` binds equivalent recovery attempts to one owner/actor/installation/capability/input operation. If the response is lost after the catalog switch, `resume.operations.read` reconciles the committed result; different input under the same operation fails with `idempotency_conflict`. CAS conflict retains the local value and exposes the durable server value for an explicit owner choice.

`interview_recovery_discard` clears only the recovery value. `interview_progress_submit` atomically clears it and links exactly one submitted visible turn, either by reusing the source already linked to a newly confirmed fact or by creating a turn linked to an existing confirmed duplicate. Recovery content is never independently projected into sources, facts, definitions, inference snapshots, Career documents, or normal logs. Content-free save, restore, discard, and conflict audit events carry only authority, operation, state, and opaque target metadata.

## Migration, transfer, history, and retention

Schema version 4 is active and write-only-current; current packages read versions 2–4. Startup retains the deterministic `resume-data.schema-0-to-1`, `resume-data.schema-1-to-2`, and `resume-data.schema-2-to-3` steps, then runs `resume-data.schema-3-to-4`. The 2→3 projection preserves every historical schema-2 revision byte and catalog extension, adds one deterministic coverage head per active confirmed employment record, maps only the recorded `complete_for_now` dimension to `deferred`, leaves missing dimensions `unanswered`, and never converts unknown, N/A, skipped, or deferred dispositions into facts. The 3→4 step is catalog-only: it preserves every schema-3 record byte, locator, operation, and extension; adds only deterministic migration provenance; and creates no quality report, quality state, corrected approval, or inferred pass. New immutable inference snapshots omit legacy non-fact job-evidence revisions even when a caller supplies their IDs.

Each migration step snapshots the prior catalog, records transformer/source/result/recovery provenance, validates a complete staged catalog, and switches the pointer atomically. Injected failure at snapshot, record, staged-catalog, marker, or post-switch boundaries restores the exact prior catalog; restart removes or reuses deterministic artifacts without duplicating heads. A schema newer than the package's declared range remains byte-unchanged and blocks activation, restart, update, or rollback with an owner-safe repair/export state. After schema-4-only writes, an older package must refuse the data; the retained schema-3 snapshot or owner export is the recovery path.

Whole-memory migration export, migration import, remote backup, and backup restore call the same namespace validator. Export/backup reject a corrupt source graph; import/restore validate the staged graph before replacement and the live graph before success, using their existing rollback behavior. This does not change migration-archive vault/master-key semantics. Audit records contain logical identities, versions, digests, counts, outcomes, and error categories only; archive paths and record content are excluded.

`recordHistory` returns revision identity, sequence, type, lifecycle state, predecessor, timestamp, and digest without a locator or path. The explicit owner-data export contains the complete validated record/operation graph plus compatibility and retention policy in a private JSON file; its public receipt exposes only a safe file name, counts, schema version, and digest.

Lifecycle activation and active-runtime restart revalidate retained owner data against the verified package manifest. Default uninstall first revokes app authority, then removes only abandoned transaction/staged-catalog state through the owner-data adapter. Durable records, recovery snapshots, referenced provenance, metadata receipts, and owner exports remain. Reinstall creates a new installation and grant, validates the retained graph, and never revives the prior token or grant. Whole-memory import/restore and lifecycle mutations are mutually excluded by the gateway migration guard. No starter-pack files are changed by M6 because the namespace is isolated and existing customized owner files remain outside its migration transformer.

Interview turns follow the same retained owner-data lifecycle: they survive process/container restart and default uninstall/reinstall, and they are included in whole-memory backup, restore, migration, and explicit owner-data export. Capability and lifecycle audit events remain content-free, so interview questions and answers do not enter normal diagnostics or support bundles.
