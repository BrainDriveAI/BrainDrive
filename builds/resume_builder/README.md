# Resume Builder package and sandboxed owner surface

This remains a separately buildable package. Version 4.2.7 declares twelve app-visible inference operations, immutable purpose policy resources, the pure durable-state workflow reducer, a private app action planner, a chat-first workspace presentation, app-owned workspace documents, and the sandboxed owner resource at `resources/main.html`. Coverage, strategy, tailoring-plan v2, product craft evaluation, one bounded craft repair, owner document review, and artifact-parity recovery are active as a review-only Spec 07 Milestones 2-6 implementation candidate.

Resume Builder is a separately developed installed app, not a BrainDrive first-party product module. Its reusable division of responsibility with the generic host is documented in the [installed app architecture guide](../../docs/developers/integrations/installed-apps.md); this README remains authoritative for Resume Builder-specific behavior.

The normal owner launch is the `Launch` chat workspace declared by the package manifest. That workspace exposes Conversation, `Your Resume Profile`, `Your Resume`, and advanced digest-bound app resources. `Your Resume Profile` is the app-owned durable document `resume.profile` bound through `resume.profile.current`; `Your Resume` is the app-owned durable document `resume.document` bound through `resume.definition.current.general`. BrainDrive stores and exposes those records through the generic app document APIs under owner/app/installation authority; they are not BrainDrive Resume-domain projections or a separate chat-only browser store. The existing structured surface remains packaged at `resources/main.html` and bound to `ui://resume-builder/main`, but it is declared as an internal surface presentation only.

Resume Builder owns its product workflow, prompts, action identifiers, action input/result semantics, output schemas, app documents, state reducers, renderer inputs, artifact sources, and terminal recovery policies. BrainDrive provides generic app hosting, package verification, capability mediation, storage authority, document bindings, model-session tool exposure, provider execution, artifact/export controls, owner confirmation, content-free audit projection, retention enforcement, and uninstall policy. The host treats Resume action ids such as `resume.profile.update` and `resume.create` as opaque app-owned meanings and dispatches only the declared capability, schema, authority, confirmation, idempotency, and audit contract.

The resource uses only the MCP Apps bridge. It implements direct/Career preflight, plain-language fact capture, exact pause/resume, and a confirmed-fact review where owners can edit, remove, add another job, or reopen a job interview before generating a resume. Each confirmed employment fact receives explicit coverage for responsibilities, accomplishments, outcomes, tools, scope, and progression. Confirmed answers are reconciled across every dimension they explicitly demonstrate before another question or Complete-for-now disposition is selected, so known outcome, scale, tool, or progression evidence is not mislabeled deferred. A pure strategy-neutral policy ranks the highest-value eligible opportunity; the model may phrase that selected opportunity but cannot change its opaque identity, job, dimension, subtype, or value category. The owner sees current coverage, rationale, honest answer shapes, and accessible Back, Skip, Unknown, Not applicable, Complete-for-now, Add more, Reopen, and Ask-another-way controls. Complete-for-now atomically defers every genuinely unanswered dimension. Non-fact choices update coverage only. One factual submission may produce multiple owner-visible units, but it opens exactly one host confirmation group with individual accept/reject decisions and persists only confirmed units. Qualitative and optional metric opportunities have separate stable identities; a declined equivalent stays suppressed across restart until explicit reopen or materially new confirmed context. Exact submitted visible turns are durable owner-data provenance, while hidden prompts and unsent drafts are never included. Owner confirmation, provider execution, durable storage authority, document binding, artifact registration, destination save, and audit are host services; Resume workflow, inference, deterministic rendering input, artifact source, and state transitions remain app-owned.

Before general generation, the resource creates and persists one current strategy, then shows its owner-readable history shape, section order, optional-summary choice, role emphasis/density, must-use count, omissions, and unresolved-gap count. Correct-information and reopen controls return to the existing fact/coverage paths; Refresh plan reruns the bounded strategy purpose. This inspection is not a fact confirmation or approval. General generation then binds the exact strategy, fact/coverage heads, prompt and quality policy identities, and the same opaque provider/model IDs. Provider failure or identity drift writes no definition.

Before approval, the resource requests and persists a score-free C1–C7/T1–T3 product craft report over the current proposal and its exact strategy/target context. The provider returns only ordered judgments for the applicable criteria, with verdicts, evidence-catalog indexes, and concise findings. The app derives immutable criterion, evidence-reference, digest, finding, target-not-applicable, and overall-verdict fields, then validates the assembled report independently. Each provider attempt has a 50-second deadline inside the host's 120-second operation budget. Two invalid responses produce a complete evidence-limited failing report and never a pass. The surface renders the domain's typed state, copy, findings, and allowed actions without translating a raw verdict. Blocking findings precede secondary guidance. Run review, bounded repair, add evidence, manual revision, owner approval, prior-version retention, and exit remain separate controls; only `product_craft_passed` exposes approval. The repaired successor is never auto-approved and must be reviewed again. Missing, stale, failing, incomplete, and evidence-limited review states cannot create ordinary owner approval.

Tailoring has a second materiality check after generation. A separate targeted resume is created only when each supported planned change causes an observable, useful wording or ordering difference. Punctuation, capitalization, or whitespace alone finalize the saved target analysis through the honest `no_material_resume_change` route; the surface keeps the general resume and creates no targeted definition or variant.

Spec 07 Milestone 5 returns the app-prepared Career summary v2 after approval through a reviewed host capability. Its deterministic operation identity makes response-loss retry idempotent, and the journal projects only the exact approved revision, narrow quality label, and current product-craft report revision when applicable. The gateway separately publishes unchanged approved-resume Markdown plus validated optional quality metadata through the generic app-published document provider. Career's normal read-only document viewer displays that metadata outside the Markdown body; publication or parity failure falls back to the latest verifiable prior approval without changing approved data or prior Career content.

Spec 07 Milestone 6 separates that independent review from the one final owner approval. The proposal surface consolidates current evidence coverage, strategy, target-fit, craft findings, intentional omissions, and unresolved uncertainty without a score or prediction. Preview consumes a strict host parity result and disables only representations that failed independent reconstruction; verified clean text remains selectable when safe and the approved source stays unchanged. Host dialogs expose screen-reader names/descriptions, initial focus, Tab containment, Escape cancellation, and focus restoration. Semantic interaction diagnostics require zero redundant confirmations, zero non-fact dialogs, at most one grouped fact confirmation per submission, and one final approval. The numeric release threshold remains blocked on `RB7-OQ-2`; this implementation does not invent one.

Spec 10 Milestone 3 extends acknowledged exact-slot recovery with truthful, bounded reconciliation. The resource still waits 1.5 seconds after editing and uses the 500 ms acknowledgement threshold only to change `Saving…` to `Still saving…`; an early operation not-found remains pending through the accepted backoff and final 120-second authoritative read boundary. Autosave and forced submit, pause, complete, back, or stage changes share the matching semantic attempt, and each guarded transition runs at most once after an exact operation/digest/revision/edit-generation acknowledgement. Multiple intents made while that same save is pending are serialized and remain valid if an earlier queued transition reloads recovery state. A genuinely newer edit supersedes every unexecuted older guard, so it cannot inherit an older acknowledgement even when its text later returns to the same value. Terminal failure and CAS conflict preserve the exact local text and expose focus-managed Retry, use-local, use-saved, and draft-only Discard controls. Workspace value/revision equality without the exact durable operation identity is fail-closed and cannot claim `Saved`. Relaunch restores only durable recovery state; teardown stops client polling and ignores obsolete UI updates without pretending to cancel durable host work. Browser storage is not used, and draft content remains outside fact provenance and inference until an existing explicit submit transition atomically clears it and links the visible turn.

Spec 10 Milestone 5 gives a safe General evidence failure exactly three focus-managed choices: `Try again`, `Review confirmed evidence`, and `Not now`. The surface discloses that retry uses the currently selected provider and may consume credits. No provider call, operation, or durable mutation occurs until the owner explicitly chooses retry; duplicate activation is suppressed. Retry creates one fresh operation with strict owner-initiated lineage while preserving the same semantic input, strategy revision, provider profile, and model. A second authoritatively equivalent evidence failure emphasizes evidence review; changed facts, coverage, strategy, provider, or model reset that emphasis. Review returns to confirmed-fact review and Not now leaves the current review state in place, both without durable mutation. Reload/direct/Career continuity comes only from authoritative host state and replay, never browser storage, and no failed draft becomes approved or Career-published content. General provider text is also checked inside the app against its exact supporting facts before persistence, including protected numbers/dates/URLs and exact structured job headings. Content-free issue IDs identify the failed rule for the second call; the app-owned deterministic fallback remains the terminal recovery after two invalid candidates.

Version 4.2.7 includes the Spec 06 Milestone 4 remembered-detail flow in addition to the Milestone 3 job-evidence interview. A returning owner can select a saved job, use an exact job-label match, choose general career context, or correct a saved fact. Ambiguous and missing matches write nothing. Exact duplicate information records the owner action without a second confirmation or regenerated resume. Confirmed changes generate one proposed general successor from the exact current fact snapshot; failure keeps the fact and approved source safe for retry.

The general proposal shows derived added, removed, corrected, and reworded statement effects. Tailored variants based on the approved source are shown as based on older evidence and are rebuilt only after an explicit owner action. Approved source and tailored records remain immutable, and Career Markdown changes only after the new general proposal is approved.

Spec 06 Milestone 5 makes History an accessible, read-only comparison surface. It lists historical proposal, approved, and retired revisions with owner-visible title, kind, job target, status, date, and version; limits checkbox selection to exactly two; and sends those exact revision IDs and expected revisions through `resume.definitions.read`. Results identify added, removed, changed, moved, evidence-reference changed, and unchanged statements with text semantics independent of color. Unchanged statements are collapsed by default and expose `aria-expanded`; result focus moves to the comparison heading; labels, live selection status, keyboard controls, responsive single-column layout, and overflow wrapping support screen readers, supported mobile widths, and 200% zoom. Unrelated or incompatible selections show a safe unavailable state and never substitute another version. The comparison path invokes neither inference nor any write capability.

Spec 06 Milestone 6 activates grounded natural-language revision for an exact approved general or targeted resume. The owner first chooses the whole resume, a section, or a statement; the exact request is persisted before classification or drafting. Presentation-only requests proceed to a bounded draft, factual or mixed requests require a distinct host confirmation first, and ambiguous requests stop for clarification without creating a proposal. Every proposal is a new immutable revision linked to the exact source definition and generating request, keeps unchanged statement identities stable, and must pass deterministic support and scope validation. Accept, owner Edit, Reject, and Regenerate are separate host-confirmed outcomes; accepting a proposal does not approve or publish it. A failed or cancelled generation keeps the durable request and approved source safe for bounded retry.

Spec 06 Milestone 7 makes clean text the always-available approved-resume recovery surface. Preview labels the exact immutable version, keeps a selectable read-only UTF-8 representation visible if PDF generation fails, and offers host-confirmed Copy, `.txt`, and PDF actions without receiving a destination path. Guidance is optional and read-only: five neutral categories cite only visible evidence labels, ask no more than three optional questions, and provide no score, ranking, prediction, guarantee, or inferred competence. Malformed or unavailable model output falls back to the same deterministic finding projection.

After a general resume is approved, BrainDrive exposes the latest approved version in Career as the read-only `General Resume` Markdown document. This uses the gateway's generic app-published document provider and document binding path, not Resume Builder-specific Career UI. The host derives and refreshes the published content from the authoritative app-owned approved definition; the sandbox receives no project filesystem access and drafts cannot replace the published version.

Resume Builder declares durable owner data for `resume.profile`, `resume.document`, approved definitions, export artifacts, export receipts, and provenance needed for recovery/audit. Disposable preview cache and transient abandoned-operation records may be physically deleted; durable owner data, provenance, operation lookup, and recovery-window records use tombstones. Uninstall revokes runtime, connection, bridge, grant, session, and token authority before executable references are cleared. Retained Resume Builder documents, artifact records, export receipts, and lifecycle evidence are unreadable by removed app code; owner-confirmed retained-data export/archive/delete controls run only while the app is `not_installed`, and reinstall receives a fresh installation/grant before any retained documents are rebound.

The interview asks for contact details, direction, jobs with associated accomplishments, education, credentials, skills, projects, leadership or volunteering, and professional links. Owners may skip any topic and revisit skipped topics from review. Follow-ups help identify outcomes without requiring metrics and never invent information. Approval refreshes the authoritative workspace and opens Preview; Preview remains available for an approved definition and History remains available whenever a definition exists.

Resume Builder owns all twelve of its inference programs in `resources/inference-program.js`: their prompts, structured output schemas, semantic issue identifiers, bounded retry instructions, candidate adjudication, and eligible deterministic fallbacks. Strategy program version 2 gives the provider only two coherent high-level enums (`history_mode` and `summary_mode`) plus a bounded rationale. The app derives every job, fact, skill, and gap identity; role emphasis and evidence density; section topology; evidence priorities; omission baseline; and persisted mode pair, then canonicalizes the complete strategy with the domain's stable code-point ordering before hashing. Its canonical ordered section vocabulary is `contact`, `summary`, `experience`, `education`, `certifications`, `skills`, `projects`, `leadership`, `volunteer`, and `links`; the valid maximum is derived from that vocabulary. The provider therefore cannot manufacture or misbind an app identity. Remaining malformed provider fields receive content-free field-specific issue IDs, and the app falls back to its own valid strategy only after the second malformed response. For General generation, the app deterministically creates every role, section, summary, evidence-support, omission, and stable statement-identity slot before provider execution. Evidence for the same job and dimension is grouped into at most six bullet slots; the provider returns only a title and text for the exact required slot IDs, so it cannot construct or alter the resume topology. Missing, extra, empty, or oversized slot text produces the content-free `schema-slot-texts-invalid` issue plus exact opaque slot diagnostics for the one bounded retry. Both attempts retain explicit must-use and summary closures, while app assembly makes representable must-use coverage and the summary count structural. Presentation-preference facts remain planning inputs and cannot become evidence bindings. The deterministic General fallback preserves multi-role headings with confirmed employers, locations, and dates; bounds and deduplicates role bullets; places certifications, projects, leadership, and links in their canonical sections; and composes its summary only from cited career facts. The installed app process exposes these programs through private model-visible tools. BrainDrive provides only the generic, app-scoped provider executor and enforces authorization, credential isolation, cancellation, the two-call ceiling, and no-tool model execution. The app never receives provider credentials or owner filesystem authority. There is no contract-version-1 Resume inference route.

The synthetic provider used by isolated browser tests is also app-owned at `test/installed-provider-fixture.mjs`. The test runner supplies it through BrainDrive's generic provider-resolver dependency; the production gateway contains no Resume fixture import, environment switch, or response-shaping branch.

Every purpose now uses the same app-owned lifecycle: canonical immutable input, a strict unknown-field-rejecting JSON Schema, independent semantic adjudication, one issue-guided repair request, and a hard two-provider-call ceiling. Failed candidate text is transient provider context only. It is never persisted, audited, rendered, or included in support evidence. Accepted and fallback results retain prompt-policy and canonical input/output digests; generation remains unapproved until a separate host-authorized persistence and owner-approval transition.

Terminal recovery is deliberately purpose-specific:

| Purpose | App-owned second-invalid policy |
|---|---|
| Interview assistance | Ask one deterministic optional question for the exact selected opportunity. |
| Resume strategy | Construct the complete canonical evidence-shaped strategy locally. |
| General resume draft | Construct the full unapproved evidence-bound draft locally. |
| Job-description analysis | Fail safely and retain the saved description; never fabricate requirements. |
| Requirement-to-evidence matching | Classify unresolved rows conservatively as unsupported or clarification-needed. |
| Tailoring plan | Return `no_meaningful_change`; preserve the General resume. |
| Targeted resume draft | Return `no_meaningful_change`; create no targeted child. |
| Revision classification | Return `ambiguous` with one deterministic clarification request. |
| Revision draft | Fail safely and preserve the selected version for manual editing or clarification. |
| Resume guidance | Project deterministic neutral guidance with no scores or predictions. |
| Product craft evaluation | Return a complete evidence-limited failing report when immutable bindings permit it; otherwise fail safely. Fallback never approves. |
| Bounded craft repair | Fail safely, preserve the proposal, and leave the existing owner actions available. |

App issue IDs are namespaced, field-specific, content-free identifiers. The exact IDs are reused in the repair instruction, terminal diagnostic, sanitized test/support evidence, generic host transport, and this app's owner-safe guidance. They never contain field values, resume text, facts, job-description text, paths, or provider output.

`RUNTIME_ENABLED` is therefore `true`: the installed package has app-owned runtime behavior even though this source package does not expose a standalone `start` or `dev` script. Its signed runtime is supervised by the generic app platform; it is not a BrainDrive core service, Docker service, or desktop sidecar.
