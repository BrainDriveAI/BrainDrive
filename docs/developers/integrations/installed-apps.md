# Installed app architecture and ownership boundary

**Maturity: internal beta for reviewed, same-release apps.** This is the current architecture used by Resume Builder and Brief Builder. It is not yet a public plugin SDK, an arbitrary-package execution promise, or a cross-version compatibility guarantee.

## The governing rule

An app owns everything that makes that app useful. BrainDrive owns only the reusable authority, isolation, transport, and provider mediation needed to run installed apps safely.

| Concern | App-owned | BrainDrive host-owned |
|---|---|---|
| Product behavior | Workflow, UI resource, domain language, prompts, output schemas, semantic validation, issue IDs, retry instructions, deterministic fallback | No app-specific product policy |
| Package identity | Declared app/publisher identity, version, immutable files, runtime artifacts, primary `ui://` resource, provenance, SBOM, requested capabilities and inference purposes | Signature/trust verification, exact reviewed registration join, install/update/disable/uninstall state |
| Runtime | Signed app process and its public/private MCP tools | Starting only installed active app runtimes, health/readiness, restart limits, connection identity, teardown and revocation |
| UI | Opaque-origin app view and owner-facing workflow | Verified resource loading, double sandbox, CSP, bridge limits, focus/close state, browser actions and confirmations |
| Data | App-defined inputs and domain transitions through reviewed capabilities | Owner/app-scoped authority, exact data adapter, CAS/idempotency, durable store boundary, audit projection and retention enforcement |
| Artifacts and exports | App-owned artifact source, renderer, bytes, label, media type, digest, and retention declaration | Generic artifact registration, owner destination confirmation, overwrite policy, safe-label validation, cancellation, app-scoped idempotency, audit, and content-safe receipts |
| Inference | Program identity, prompt, strict JSON Schema, candidate adjudication, content-free issue IDs, one correction instruction, eligible fallback | Owner-active provider resolution, credential isolation, structured no-tools execution, cancellation, two-call ceiling and generic terminal envelope |

Resume Builder and Brief Builder are reference implementations of this model, not BrainDrive product modules. A future app must carry its own policy and behavior in its signed package rather than adding that app's semantics to the BrainDrive runtime.

## Installation and launch flow

1. A generic manifest revision 2 declares immutable package files, supported platform artifacts, its primary `ui://` resource, requested capabilities and inference purposes, provenance, SBOM, and the retention policy matrix.
   It may also declare generic presentation metadata for current app workspaces. Existing surface-only packages remain valid because `primary_resource` stays required. Optional chat-workspace descriptors are declarative only: they list presentation profiles, workspace documents, digest-bound package resources, purpose-limited context requests, and app action descriptors without granting runtime authority or naming host handlers. App action descriptors must include digest-bound, resolved input and result JSON Schema bodies; opaque schema IDs alone are rejected for app-chat manifests.
   The additive SC-001 package-component contract covers the next generic sidecar package shape without changing the current installed-app runtime path. A conforming package-component manifest can describe launchable app components, capability-provider components, combined packages, dependency services, app-owned sidecars, provider sidecars, provided operations, capability dependencies, target matrices, vault-backed secret declarations, permissions, lifecycle policy, diagnostics, retention, and evidence policy. Passing that contract is only admission evidence; it does not install the package, start a sidecar, route an operation, render a provider card, generate Docker configuration, or qualify desktop behavior.
   The additive SC-002 package store persists validated package/component records for that contract and can include a redacted `packages` array in `GET /apps`. That projection lists safe package identity, component kind, lifecycle state, health class, operation IDs, dependency IDs, target labels, retention class, and generic dependency readiness only. Required dependency failures remove launch/start action labels and project blocked operation IDs; optional failures project degraded operation IDs. It omits package paths, adapter entrypoints, sidecar bindings, endpoints, local ports, host paths, credentials, raw provider payloads, and internal runtime names. The existing `apps` array and reviewed app lifecycle routes remain the launch/install authority for Resume Builder and Brief Builder; SC-002 does not start sidecars, register provider routes, switch providers, or add package lifecycle mutation routes.
   The additive SC-003 sidecar supervisor starts, checks, restarts, stops, and uninstalls installed sidecar components through runtime-kind drivers selected from package descriptors. It creates private in-memory runtime bindings and exposes raw authority only to the declared provider adapter or owning app component. Consumers, unrelated components, and app code cannot start arbitrary sidecars or read bindings. Owner-safe snapshots and diagnostics carry only component identity, target label, lifecycle/health state, restart attempt, transport class, audience class, and typed error code; they omit raw endpoints, local ports, bearer material, process/container identifiers, host paths, package paths, credentials, provider payloads, Docker live claims, desktop packaging claims, and capability routing. SC-008 adds Docker dev/local package-sidecar rendering: Compose override services and runtime descriptor files are generated from sidecar target metadata instead of provider-specific static services. Desktop staging includes the package manifest for compatibility evaluation but does not claim SearXNG desktop support because no non-Docker packaged sidecar artifact is qualified.
   The additive SC-009 diagnostics contract generalizes provider-package operation receipts, sidecar lifecycle diagnostics, support-bundle posture, bounded retention, and qualification-staleness rules. Diagnostics remain Host-owned and content-free by default. They can expose only safe package/component/operation identity, selected-policy class, status, typed failure code, count/timing classes, target label, transport class, and stale-evidence classes. They do not expose raw provider responses, page content, prompts, credentials, endpoints, local ports, host paths, owner-private content, internal network details, or raw support-bundle provider payloads. Manifest, adapter, sidecar/runtime target, provider version, operation contract, network/permission, retention/diagnostics, or security-boundary changes stale affected qualification evidence until rerun.
2. BrainDrive verifies the descriptor, archive digest, signature, trust root, revocation state, compatibility, and selected platform artifact.
3. `FirstPartyAppRegistry` joins the verified package to an exact reviewed app/publisher/route registration. A manifest cannot select a host handler, import a module, or grant itself authority.
4. Installation persists lifecycle and grant state. The supervisor starts a packaged runtime only for an installed active app and binds it to the exact installation, package digest, runtime identity, and lifecycle generation.
5. The modern MCP client negotiates the pinned protocol and Apps extension, discovers tools/resources, and reads only the verified primary resource from the same server.
6. The trusted web layer renders that resource through a fixed cross-origin proxy and an inner opaque-origin sandbox. The app view receives safe presentation context, never bearer credentials, host paths, owner permission objects, provider secrets, or direct gateway/Tauri authority.
7. Every capability call re-resolves the selected app and checks its current install, package, connection, view, operation, grant, revocation, scope, deadline, and idempotency binding before invoking one reviewed adapter.

Disable, update, uninstall, lifecycle-generation change, failed health, session close, and gateway shutdown revoke or replace the corresponding runtime, connection, bridge, and token authority.

## Retention, uninstall, update, and reinstall

Generic app manifests declare a retention policy matrix with these classes: runtime authority, verified package code, disposable cache, app storage, artifact records, export receipts, owner exports, and lifecycle tombstones. BrainDrive validates the matrix at package verification time. Runtime authority, app code references, unshared package bytes, and disposable cache must be removed on uninstall. App storage, artifact records, export receipts, owner exports, and lifecycle evidence are projected from the manifest, not from app-specific host branches.

Uninstall always revokes runtime, connection, bridge, grant, session, and token authority before clearing executable references. Durable owner data can remain present after uninstall, but removed app code cannot read it. Retained app storage, artifact records, and export receipts expose only trusted owner-confirmed post-uninstall controls: delete, export, and archive. These controls require the selected app to be in `not_installed`; active, disabled, quarantined, or recovering apps cannot use retained-data deletion or retained-data export/archive paths.

Reinstall is a fresh lifecycle transition. It creates a new installation and grant, revalidates the selected package and data compatibility, and can reconnect retained data only through that new authority path. A package update follows the same compatibility gate before switching the active package pointer; incompatible retained owner data is preserved and the lifecycle fails closed rather than silently rewriting or deleting it.

Generic app document storage is owner/app/installation scoped. Document records retain the package digest, lifecycle generation, grant id, grant revision, and revocation generation that created or last updated them for audit, but read and list access do not require those historical fields to equal the current package or grant. The host rebinds the namespace to the current active authority before active-session storage access. Writes and deletes require that current binding, so a stale package, lifecycle generation, grant revision, or revoked grant cannot mutate documents after the host has advanced authority.

The generic document store supports create, read, update, list, and delete. Create uses `expected_revision: null`; update and delete use revision compare-and-swap; all mutations are idempotency-keyed and reject changed canonical input under the same key. Listing is a full current-document projection for the selected owner/app/installation namespace, separate from the content-free audit projection. Delete defaults to a tombstone: document content is removed from the current read/list surface, the next revision is recorded as a tombstone, and audit projection contains only identifiers, revision metadata, retention class, prior content digest/size, delete mode, and timestamps. Physical content deletion is allowed only for disposable/transient retention classes; durable owner data, provenance, operation lookup, and recovery-window records require tombstones.

For example, a notes app could declare `notes.source`, `notes.summary`, and `notes.preview` workspace documents, plus `notes.summary.generate` and `notes.summary.approve` action ids. BrainDrive would validate the manifest, bind those documents to the owner/app/installation namespace, expose only declared model-session tools, enforce confirmation and idempotency, mediate any export, and apply the declared retention policy. The meaning of "source", "summary", "preview", "generate", or "approve" would remain in the signed notes package and reviewed app adapter, not in BrainDrive core.

## App-chat workspace sessions

Packages that declare a `chat_workspace` presentation can be opened through an additive app-chat session path. The host selects the requested presentation or package default, requires an active installation and current grant, and binds the session to owner, account, actor, app, publisher, installation, package digest, presentation id, workspace id, view id, grant id/revision, revocation generation, lifecycle generation, and a digest of the granted context set. Current local-owner installations do not expose a distinct account object, so the account binding is the owner id until a separate account authority exists. App-chat sessions expire after five minutes without validated activity, but successful session inspection, document access, and model-context assembly renew that inactive window. The web shell sends a bounded heartbeat while an app-chat workspace is open and retries a document save after session recovery when the original session has expired. Successful document saves show explicit owner feedback and document-chrome views return to the rendered preview; stale close failures during relaunch or teardown remain best-effort cleanup and do not block returning to Apps.

The web shell renders descriptor-backed app-chat workspaces with the same responsive navigation model as the host shell. Desktop layouts use a persistent left rail for workspace documents, resources, settings, and return-to-apps controls. Phone-width layouts replace that rail with a hamburger header and fixed navigation drawer, preserving the same app-owned items without introducing a separate mobile-only app contract.

Owner-editable app resources use a generic copy-on-write contract. The immutable package file remains digest verified and read-only, but a resource with `owner_editable: true` must also declare an editable workspace document for the same `resource_id`, a host `data_binding_id`, and matching package-file `initial_content` with `seed_policy: "when_missing"`. The host seeds that owner-owned document on first read and all later edits are ordinary app document writes with revision CAS. Model-session prompt assembly reads the owner override for owner-editable resources and records source/revision evidence; non-editable resources continue to read the verified package file. Resume Builder applies this to Agent Instructions and Interview Guide. Its quality standard, template standard, recovery guidance, and formatted Resume stay read-only.

The app-chat session launch API does not execute model actions by itself. Native chat messages that carry a current `app_chat` metadata envelope now receive an app-generic model context: the gateway re-resolves the selected app host, rechecks session/lifecycle/grant/package/presentation/workspace/context-digest authority, appends digest-bound package resources selected by descriptor prompt-inclusion policy, and exposes only that workspace's `model_exposure: available` actions as session-scoped tools. Those tools treat action ids as opaque app-owned semantics. When the active runtime exposes the private `app.actions.plan` tool, an action may declare zero or more required host capabilities, and BrainDrive asks the app to translate the opaque action into a strict ordered plan of generic `capability.call`, `document.read`, `document.write`, and `export.prepare` steps, using only the app input and current app-owned document snapshots. Without a runtime planner, V1 model-session actions must declare exactly one host capability, and BrainDrive dispatches the exact app-provided input through the generic app capability dispatcher keyed by app id, capability name, and version. The dispatcher enforces reviewed host registration, manifest request, current grant, confirmation, idempotency, cancellation, timeout, input/result validation, and audit projection, and returns recoverable safe failures for malformed, stale, hidden, undeclared, wrong-scope, ungranted, expired, or digest-mismatched calls. When a prepared export action returns a generic PDF/text artifact, the web shell observes that transient tool result, validates the payload with the host browser policy, starts the local browser/native download, finalizes the generic receipt under the same app key, and shows a chat-visible host notice with only the safe filename and outcome. Existing sandboxed Apps launches continue to use the primary resource and app bridge path.

The web Apps surface routes visible primary `chat_workspace` presentation metadata to a native BrainDrive workspace shell. That shell is generic: it renders Conversation through the existing native chat panel, lists descriptor-backed workspace documents, groups advanced package resources under Advanced, keeps Back to Apps and Close controls host-owned, and keeps the native composer available from document/resource views for follow-up chat. It displays resource metadata such as title, media type, prompt-inclusion policy, and digest, but it does not read package resource contents, host filesystem paths, app HTML, bridge tokens, provider credentials, or raw grants into the UI or chat metadata. Surface presentations and packages without a visible primary chat workspace continue through the sandboxed app frame.

Workspace document descriptors may declare presentation metadata for host-rendered views. The current generic renderers are plain text, Markdown document, paper document preview, and JSON editor. Header actions are descriptor-owned but host-rendered: examples include returning to chat, queueing an app action prompt into the current chat, or opening an editable document state. The renderer choice and header labels do not grant authority; reads, writes, app actions, and exports still recheck the active session and the app's declared capability/schema contract.

Owner catalog projection includes only safe presentation summaries: version, default presentation id, labels, descriptions, profile ids, profile type, owner visibility, and either workspace id or primary resource URI. It omits workspace documents, actions, resource package paths, prompt-inclusion policy, resource contents, and digests. Resume Builder uses this path to make `Just Chat With It` the primary launch while retaining its structured surface as an internal presentation.

Generic package-component projection is a separate additive catalog field. When configured, `GET /apps` returns `packages` beside `apps`. Provider-only and dependency-service package components are marked `launchable: false`; sidecars appear as package components with safe lifecycle/health classes rather than private runtime connection data. The Apps web surface consumes this projection as an owner lifecycle section for apps, capability providers, dependency services, and sidecars. It shows safe state, health, version, operations, dependencies, target labels, retention classes, dependency readiness, and host-projected lifecycle action labels. Required missing, disabled, unhealthy, unsupported, unavailable, selection-required, or ambiguous generic operation dependencies appear as blocked readiness with no launch/start label; unknown readiness is visible and is not treated as ready. Optional failures appear as degraded readiness and never cause silent provider install, sidecar start, provider switch, direct endpoint disclosure, or claims that web lookup succeeded. Selection-required copy points to owner/admin policy without adding app-owned provider selection controls. Search/Read dependencies disclose that queries and URLs may be sent to the selected provider, provider keys and unrelated owner data are not sent, owner-managed provider costs remain outside BrainDrive, and denied or revoked approval leaves Search/Read unavailable. Provider-only and dependency-service packages do not get Launch controls unless the projection contains a launchable app component. Package action labels remain non-executing UI controls until a later accepted package lifecycle route adds mutation authority.

Context projection and model prompt assembly are descriptor-limited. The host evaluates only the selected workspace's declared `context_requests`, requires each request's capabilities to be present in the current grant, and projects supported sources through existing host capability boundaries. The current implemented source is bounded Career context via `career.context.read`; unsupported optional context appears as unavailable metadata, while required unsupported or ungranted context fails closed. App-chat projections and prompt resources do not include bearer tokens, provider credentials, owner permission objects, host filesystem paths, destination paths, or arbitrary memory traversal authority.

## App-owned inference flow

Installed inference uses contract version 2:

1. The sandbox requests `app.inference.request` through its app-bound bridge; it cannot call the provider or private program tools directly.
2. BrainDrive consumes a one-use `app_inference` token and invokes private prepare/adjudicate tools on the same verified app connection.
3. The app prepares the exact system/user messages and strict JSON Schema for attempt one.
4. BrainDrive resolves the owner's active provider and performs one structured completion with no tools. Credentials remain only in the adapter authorization boundary.
5. The app adjudicates the parsed candidate. It either accepts, returns namespaced content-free issue IDs for one correction call, fails safely, or uses an eligible deterministic app fallback after the second invalid result.
6. BrainDrive returns the generic terminal envelope: app program and operation identities, attempt count, completion mode, opaque provider/model identities, issue IDs, structured app result, and app-supplied persistence binding where required.
7. The app separately requests its reviewed data capability to persist an unapproved result. Normal domain, evidence, CAS, review, and owner-approval gates still apply.

Failure transport follows the same ownership boundary. BrainDrive validates and forwards only a strict app-neutral safe envelope containing a stable code, fixed safe message, retryability, correlation or operation reference, attempt count, completion mode, namespaced content-free app issue IDs, owner state, and bounded scalar app recovery metadata. It never replaces the stable code with an exception message, and it drops content-bearing or malformed fields. Each installed app owns the mapping from its issue IDs to owner guidance. Future apps can reuse this transport without adding their schemas, validators, prompts, fallback constructors, or policy branches to BrainDrive.

Provider output is not durable merely because inference completed. Persistence is a distinct host-authorized transition. Equal retries may coalesce or replay through the operation coordinator; changed canonical input under the same semantic identity conflicts. Cancellation propagates to provider work, and late responses cannot commit.

Artifact/export output follows the same reusable split. An app may produce a PDF or text payload, owner-visible label, source identity, digest, media type, and retention class, but BrainDrive registers the artifact under current app/install/package authority and owns destination confirmation, overwrite confirmation, safe-label enforcement, cancellation, audit, browser/native download initiation, and receipt projection. Native app-chat workspaces keep export bytes transient: the stream observer hands prepared bytes directly to the trusted save helper and stores only status plus the safe filename for chat-visible user feedback. The app never receives raw filesystem paths, owner destination handles, provider credentials, or host authorization tokens; replay returns the same safe receipt projection by app-scoped operation and idempotency identity.

Reference apps demonstrate the reusable boundary:

- Strategy inference exposes only bounded high-level choices to the model; the app derives all job/fact identities, topology, evidence priority, and persisted bindings.
- General Resume inference gives the model exact text slots; the app owns statement IDs, support identities, section/role topology, the six-bullet maximum, fact-grounding checks, issue IDs, and deterministic fallback.
- Brief Builder declares different document ids, action ids, data capabilities, and inference purpose while using the same chat, document, tool, artifact, export, retention, and lifecycle paths.

These patterns keep app semantics out of BrainDrive while still allowing the host to enforce generic safety and resource limits.

The same boundary applies to test support. An app-specific synthetic provider or response shaper lives with that app's tests and is injected into the isolated test gateway through the generic installed-app provider-resolver dependency. Production gateway source must not import an app fixture or select one through an app-named environment branch.

## Scaling across many available apps

The catalog and reviewed registry hold bounded metadata; they do not execute every available app. An app runtime is started only after that app is installed and active, and provider work occurs only when an authorized invocation requests it. Live views, connections, tokens, operation state, and data scopes are keyed by app and installation.

Therefore, having 100 available apps while an owner installs four does not load 100 app workflows, prompts, validators, or provider sessions into the core runtime. The installed four pay their own runtime and active-view costs. BrainDrive retains only generic registry/lifecycle infrastructure plus the metadata required to discover and verify available packages.

Current reviewed registrations are compiled same-release integration points. A future public marketplace needs a separately accepted extension and compatibility policy; do not treat the present internal registry as an unrestricted dynamic plugin ABI.

The package-component conformance gate preserves the same authority rule for sidecars and providers. Manifest fields that attempt to name Host handlers/imports, private runtime bindings, endpoints, ports, raw provider responses, host paths, credentials, or internal service names fail closed. Public sidecar binds, unmanaged secret delivery, unsupported runtime targets, missing operation contracts, and silent provider install/switch policy also fail closed with typed contract errors. These checks are generic infrastructure for later SideCar roadmap ids; SearXNG is only one proof fixture and is not the generic runtime model.

## Checklist for another app

1. Create a separately buildable app package with a generic revision-2 manifest, immutable primary resource, packaged runtime artifacts, provenance, and SBOM.
2. Define a unique canonical app/publisher/route identity and request only the minimum capabilities and inference purposes.
3. Add an exact reviewed registration for each capability, inference purpose, data adapter, runtime profile, and lifecycle binding. The manifest alone cannot create these bindings.
4. Implement public app-visible tools/resources and keep inference prepare/adjudicate tools private from the iframe.
5. Keep workflow, prompts, schemas, semantic validation, issue IDs, retry instructions, and fallbacks inside the app package.
6. Use host capabilities for owner data, exports, browser actions, confirmations, and inference. Do not add filesystem, credential, provider-selection, or unrestricted network authority to the app.
7. If package defaults are owner-editable, declare them as immutable resources plus seeded bound workspace documents. Do not add host branches for app-specific resource ids.
8. Make durable writes idempotent and revision-bound. Treat transport loss as ambiguous until the host's operation/reconciliation read resolves it.
9. Test package verification, lifecycle/revocation, cross-app isolation, sandbox denial, capability scope, inference cancellation/replay, content-free audit projection, and app-specific domain behavior.
